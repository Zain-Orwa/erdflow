# ERDFlow Scale Strategy

**Document:** `docs/SCALE.md`  
**Status:** Scale Strategy v0.1  
**Product:** ERDFlow  
**Scope:** Desktop-first, local-first, scale-ready architecture

---

# 1. Purpose

This document defines what “scale” means for ERDFlow and how the product
should prepare for it without over-engineering the first desktop release.

ERDFlow is a desktop-first application.

Scale therefore has two different meanings:

1. **Local scale**
   - large diagrams,
   - large projects,
   - large imports,
   - many attributes,
   - expensive conversions,
   - responsive editing,
   - bounded memory use.

2. **Future ecosystem scale**
   - many installed clients,
   - future cloud services,
   - collaboration,
   - shared projects,
   - background workers,
   - future AI workloads,
   - potentially millions of users across the wider ecosystem.

The immediate engineering priority is local desktop excellence.

The long-term architecture must avoid decisions that would make future
service-scale evolution unnecessarily difficult.

---

# 2. Scale Principle

ERDFlow follows:

> Local-first experience, scale-ready architecture.

This means:

```text
TODAY

Desktop Application
        ↓
Local Core
        ↓
Local Project File
```

and later, if needed:

```text
FUTURE

Desktop / Other Clients
        ↓
Service/API Layer
        ↓
Project / Collaboration / AI / Search / Workers
        ↓
Storage / Cache / Observability
```

We do not build the future distributed system now.

We only preserve clean boundaries that make such evolution possible.

---

# 3. What Scale Does NOT Mean

Scale does not mean:

- adding microservices to the desktop application,
- adding distributed infrastructure before it is needed,
- introducing a message broker for local canvas edits,
- moving all features to the cloud,
- forcing online accounts,
- making the desktop client dependent on remote services,
- adding complex thread synchronization everywhere,
- optimizing code without measurement,
- assuming C++ or Rust automatically makes software fast.

The product must remain understandable and maintainable.

---

# 4. Immediate Scale Targets

ERDFlow should eventually handle projects containing at least:

```text
Hundreds of entities
Thousands of attributes
Many relationships
Multiple conceptual pages
Large schema models
Large physical models
Large SQL outputs
Large imported files
```

The exact supported limits are not locked in v0.1.

Before release, measurable target sizes should be established through
benchmarks and real project examples.

# 5. Performance Priorities

The most important user-facing performance goals are:

1. fast startup,
2. responsive window interaction,
3. smooth entity dragging,
4. smooth zoom,
5. smooth panning,
6. responsive selection,
7. low-latency property editing,
8. fast undo/redo,
9. responsive navigation between pages/workspaces,
10. predictable save/load times,
11. non-blocking imports,
12. non-blocking conversion,
13. bounded memory growth,
14. useful progress reporting,
15. cancellation for long operations where practical.

# 6. UI Thread Rule

The UI thread must remain responsive.

The UI thread owns:

```text
Rendering
Pointer interaction
Keyboard interaction
Menus / Ribbon
Dialogs
Canvas updates
View updates
User feedback
```

Heavy work should not block it.

Examples of heavy work:

```text
Large import parsing
Large project loading
Large project saving
Validation
Conceptual → Schema conversion
Physical conversion
SQL generation for very large projects
Auto-layout
Reverse engineering
Search/indexing
Future database refresh
Future AI result processing
```

# 7. Background Work Model

The architecture should support a background task system.

Conceptually:

```text
UI Thread
    │
    │ submit task
    ▼
Application Task Coordinator
    │
    ▼
Background Executor / Worker Pool
    │
    ├── Import
    ├── Validation
    ├── Conversion
    ├── Save/Load
    ├── Auto-layout
    └── Search/Index
```

The exact Qt mechanism is not locked yet.

Possible mechanisms later include:

```text
QtConcurrent
QThreadPool
QRunnable
Dedicated workers
```

The architectural requirement is separation, not a particular API.

---

# 8. Immutable Inputs for Background Work

Background tasks should prefer immutable input snapshots.

Example:

```text
Live Conceptual Model
        │
        │ snapshot
        ▼
Immutable Conversion Input
        │
        ▼
Worker Thread
        │
        ▼
Conversion Result
        │
        ▼
Application Review
        │
        ▼
Apply accepted changes
```

Background workers should not arbitrarily mutate the live Project model.

This reduces synchronization complexity.

---

# 9. Controlled Mutation

Meaningful project mutations should pass through Application commands.

Preferred:

```text
User action
    ↓
Application Command
    ↓
Domain mutation
    ↓
Result
    ↓
UI refresh
```

Avoid:

```text
Widget
   ↓
Direct shared-state mutation
   ↓
Worker thread changes same state
```

This protects:

- undo/redo,
- validation,
- change tracking,
- propagation behavior,
- thread safety.

---

# 10. Canvas Performance Strategy

The Conceptual Canvas is expected to become one of the most performance-sensitive parts of ERDFlow.

The main rule:

> Update only what changed.

Example:

```text
Dragging Student entity
        ↓
Update Student visual position
        ↓
Update connected connector geometry
```

Avoid:

```text
Dragging Student entity
        ↓
Rebuild entire scene
        ↓
Recompute unrelated elements
        ↓
Redraw everything
```

---

# 11. Incremental Rendering

Canvas updates should be incremental.

Examples:

- moving one entity updates that entity,
- connected lines update only when required,
- editing one label does not rebuild the entire scene,
- changing one property refreshes only dependent visuals,
- adding one relationship does not recompute unrelated pages.

This principle applies to both Qt presentation models and future core calculations.

---

# 12. Large Diagram Strategy

Large diagrams create several challenges:

```text
Rendering cost
Hit testing
Selection
Connector updates
Auto-layout
Search
Navigation
Memory
```

Potential strategies later may include:

- scene/view culling,
- only rendering visible items,
- cached text/geometry where useful,
- incremental connector geometry,
- spatial indexing,
- simplified rendering while zoomed far out,
- page segmentation,
- optional mini-map,
- lazy property panel population.

Exact Qt graphics choices will be decided during the Canvas phase.

---

# 13. Multi-Page Conceptual Models

Multiple pages help both usability and performance.

A large conceptual model may be split into:

```text
Conceptual ERD
├── Page 1
├── Page 2
├── Page 3
└── ...
```

Pages are organizational/layout structures.

The semantic model remains one Conceptual Model.

Inactive pages should not require unnecessary visual work.

---

# 14. Connector Performance

Relationships may create large numbers of connectors.

ERDFlow should avoid expensive full-scene connector recalculation.

Preferred behavior:

```text
Move Entity A
    ↓
Find relationships involving A
    ↓
Update only those connectors
```

Connector routing complexity should be measured before sophisticated routing algorithms are introduced.

---

# 15. Selection and Hit Testing

Large diagrams require efficient hit testing.

The system should not scan every semantic object manually for every mouse movement if the Qt scene or a spatial index can perform that work more efficiently.

This is an implementation-phase concern, but the architecture should keep semantic lookup and visual lookup separate.

---

# 16. Validation Performance

Validation should support incremental operation where practical.

Example:

```text
Rename Attribute
      ↓
Run validations affected by that change
```

instead of always:

```text
Rename Attribute
      ↓
Revalidate entire Project
```

Full-project validation should still exist for:

- explicit validation,
- conversion readiness,
- save/export checks,
- testing.

---

# 17. Conversion Performance

Conversion engines should be pure and deterministic.

Examples:

```text
Conceptual → Relational
Relational → Physical
Physical → SQL
```

Large conversions may run in background tasks.

The conversion engine should operate on snapshots rather than live UI objects.

Performance should be measured by:

```text
Input size
Number of entities
Number of attributes
Number of relationships
Conversion duration
Temporary memory
Result size
```

---

# 18. Mapping and Provenance Performance

Cross-level mappings and provenance are foundational ERDFlow structures.

They support:

```text
Conceptual Entity → generated Relation
Schema Attribute → originating Conceptual Attribute
Physical Column → originating Schema Attribute
Relationship → generated junction Relation
Current object → generation baseline
```

These lookups may occur during:

- conversion,
- regeneration,
- review,
- controlled Schema → Conceptual propagation,
- undo/redo,
- validation,
- diffing,
- debugging.

Therefore, mapping/provenance lookup must scale with project size.

A common cross-level lookup must not depend on repeatedly scanning the
entire Conceptual, Relational, or Physical model.

The exact data structure is deferred, but direct/indexed lookup by stable
identity is an architectural requirement.

---

# 19. Stable ID Lookup

As projects grow, ERDFlow must support efficient stable-ID lookup.

Conceptually:

```text
EntityId → Entity
AttributeId → Attribute
RelationshipId → Relationship
RelationId → Relation
SchemaAttributeId → Schema Attribute
TableId → Table
ColumnId → Column
MappingId → Mapping
BaselineId → Baseline
```

Implementation may use:

- hash maps,
- indexed containers,
- typed registries,
- other suitable structures.

Exact choices should be benchmark-driven.

The architecture does not require a specific complexity guarantee such as
`O(1)` for every operation before containers are chosen.

It does require that common identity and mapping lookups avoid full-model
linear scans where an indexed lookup is practical.

---

# 20. Diff and Regeneration Performance

Regeneration must protect manual work.

The architecture includes:

```text
Previous Generated Baseline
Current User-Edited Model
New Generated Candidate
```

Comparison should use:

- stable IDs,
- mappings,
- semantic change information,
- targeted diffing.

Avoid relying on expensive name-based full-model comparisons when more precise lineage data is available.

---

# 21. Undo / Redo Scale

Undo history can consume significant memory.

Undo budgeting must consider more than command count.

A command may carry:

- stable-ID references,
- old/new values,
- semantic change metadata,
- mapping/provenance deltas,
- generated patches,
- imported-data deltas,
- references to snapshots or baselines.

Therefore, the effective undo budget is closer to:

```text
Undo Cost
    =
Command Count
+
Payload Size
+
Referenced Snapshot / Delta Size
+
Mapping / Provenance Change Size
```

ERDFlow should eventually define:

- maximum history size,
- memory-aware history limits,
- command merging for repeated edits,
- compact delta storage where practical,
- treatment of large imports,
- treatment of mass conversion operations,
- treatment of mapping/provenance changes.

Example:

```text
Move Entity by 1px
Move Entity by 1px
Move Entity by 1px
...
```

should not necessarily become hundreds of independent undo entries.

A drag operation may be compressed into one semantic undo action.

Where practical, commands should reference stable IDs and compact changes
rather than carrying duplicate full-model copies.

---

# 22. Project Save Performance

Saving must remain safe and reasonably fast.

The project format should support:

- atomic save behavior,
- versioning,
- bounded temporary memory,
- progress reporting for very large projects if needed.

Do not optimize project serialization prematurely.

Measure first.

Potential later behavior:

```text

Read / Parse
    ↓
Validate

Construct domain model
    ↓
```

# 24. Import Scale

Import may become one of the heaviest workflows.

Examples:

```text
Large CSV
Large JSON
Large SQL dump
Database metadata import
Future XLSX
```

Imports should support:

```text
Progress
Cancellation
Warnings
Errors
Partial preview where useful
```

Importers must not require loading every future data source entirely into memory if streaming is possible.

---

# 25. CSV Strategy

For small CSV files:

```text
Read
Parse
Preview
Import
```

For large CSV files, future implementations may use:

- streaming parsing,
- row batching,
- bounded preview samples,
- incremental type inference.

The architecture should not require:

```text
Read entire file
→ duplicate entire file in memory
→ parse another full copy
```

---

# 26. JSON Strategy

JSON may contain:

- arrays,
- nested objects,
- large data structures.

Large imports may require:

- streaming/event parsing,
- bounded previews,
- recursion/depth limits,
- schema inference limits.

Exact parser choice is deferred.

---

# 27. SQL Import Strategy

Imported SQL is parsed as text/model input.

It is not executed automatically.

Large SQL imports may require:

- token/statement streaming,
- incremental parsing,
- bounded diagnostics,
- cancellation,
- partial recovery where safe.

---

# 28. Import Preview Scale

A preview should not require rendering all imported rows.

Example:

```text
CSV with 5,000,000 rows
```

Preview may show:

```text
Detected columns
Detected types
First N rows
Warnings
Estimated row count
```

rather than rendering millions of rows.

# 29. Data Workspace Scale

The Live Data Grid must not assume all rows fit in memory.

Architecture:

```text
QTableView
    ↓
Table Model Adapter
    ↓
Data Source
```

Possible Data Sources:

```text
LocalDataSource
ImportedDataSource
FutureDatabaseDataSource
```

# 30. Pagination / Chunking

For large data sources, ERDFlow may use:

- pagination,
- chunking,
- lazy fetch,
- windowed loading.

Example:

```text
Request rows 0–499
      ↓
Display
      ↓
User scrolls
      ↓
Request next chunk
```

Exact strategy depends on the source.

---

# 31. Sorting at Scale

Sorting behavior depends on the Data Source.

## Small local data

Sorting may happen in-memory or through a Qt proxy.

## Large remote data

Sorting should be pushed to the source:

```sql
ORDER BY created_at DESC
```

Avoid:

```text
Download 10 million rows
      ↓
Sort locally
```

---

# 32. Filtering at Scale

Same principle:

## Local

```text
Client-side filter
```

## Remote

```text
Database/source-side filter
```

Example:

```sql
WHERE status = 'active'
```

The Data Source interface should allow source-specific execution.

---

# 33. Search at Scale

Search may operate differently depending on the workspace.

Examples:

```text
Canvas search
Schema search
Project search
Data search
```

For small projects, direct search may be enough.

For very large projects, indexing may be introduced.

Do not create a search-index subsystem until measurements justify it.

---

# 34. Memory Strategy

ERDFlow must avoid accidental duplication of large models.

Potential memory risks include:

- duplicate domain snapshots,
- undo history,
- imported raw data,
- preview copies,
- conversion candidates,
- large SQL strings,
- cached canvas geometry,
- generation baselines,
- mapping/provenance indexes,
- temporary diff/review structures.

A particularly important known peak-memory scenario is regeneration.

During a safe Conceptual → Schema regeneration, ERDFlow may temporarily
need all of the following at the same time:

```text
Previous Generated Baseline
        +
Current User-Edited Schema
        +
New Generated Candidate
        +
Mappings / Provenance
        +
Undo / Change Data
```

A naïve implementation may therefore multiply peak memory use
substantially during regeneration.

The exact multiplier is not assumed in advance because models may differ
in size and future implementations may share data.

This scenario must be measured explicitly.

If necessary later, possible optimizations include:

- structural sharing,
- compact change sets,
- sparse deltas,
- immutable shared substructures,
- incremental comparison,
- releasing temporary structures as early as possible.

Memory usage should be measured explicitly.

---

# 35. Snapshot Strategy

Snapshots are useful for safe background work and regeneration.

However, full deep copies of enormous projects may become expensive.

Initial implementations may favor simple consistent copies while project
sizes remain moderate.

Important rule:

> Snapshot creation itself is part of the performance budget.

It is not enough to move conversion or validation to a worker thread if
creating the input snapshot freezes the UI first.

At the same time, a background worker must not copy arbitrary live mutable
state while the UI is changing it.

The snapshot must represent a consistent model state.

If snapshot creation later becomes expensive, ERDFlow should optimize the
snapshot mechanism rather than introduce unsafe concurrent reads.

Possible later strategies include:

- copy-on-write structures,
- immutable shared substructures,
- structural sharing,
- versioned model components,
- incremental snapshot construction where correctness can be preserved.

Do not add this complexity until profiling shows it is needed.

---

# 36. Caching

Caching may be useful for:

- expensive validation results,
- text measurement,
- generated SQL,
- layout calculations,
- search results,
- type inference.

Caching must have clear invalidation rules.

A wrong cache is worse than no cache.

Do not cache by default.

Measure first.

---

# 37. Incremental Recalculation

ERDFlow should prefer incremental recalculation where dependency boundaries are known.

Example:

```text
Change Student.Email type
      ↓
Revalidate Student.Email
      ↓
Revalidate affected relation/table
```

rather than recomputing unrelated project sections.

Dependency tracking should remain simple initially.

---

# 38. Auto-Layout

Auto-layout may become CPU-intensive for large graphs.

It should:

- run outside the UI thread,
- support cancellation where practical,
- produce a layout proposal/result,
- avoid mutating the live scene from a worker thread.

Conceptually:

```text
Graph snapshot
    ↓
Background layout engine
    ↓
Layout result
    ↓
Apply on UI/Application side
```

---

# 39. Progress Reporting

Long-running tasks should provide useful progress where progress can be estimated.

Examples:

```text
Importing 42%
Validating 70%
Generating Schema...
Saving Project...
```

Do not show fake precision.

If progress cannot be estimated:

```text
Working...
```

with cancellation may be better than an invented percentage.

---

# 40. Cancellation

Cancellation is appropriate for:

- imports,
- large validation,
- auto-layout,
- reverse engineering,
- future database scans,
- future AI operations.

Cancellation must leave the project in a valid state.

Preferred model:

```text
Worker builds result separately
      ↓
Cancelled?
      ├── Yes → discard
      └── No  → review/apply
```

---

# 41. Error Isolation

A failure in one background task must not corrupt the Project.

Examples:

```text
Failed CSV import
→ Project remains unchanged
```

```text
Failed conversion
→ Existing Schema remains unchanged
```

```text
Failed save
→ Existing project file remains intact
```

This rule is essential for reliability at scale.

# 44. Performance Regression Testing

Important operations should eventually have regression benchmarks.

Example:

```text
Conceptual → Schema
100 entities
target < previous baseline + allowed tolerance
```

Performance tests should detect major regressions.

They should not produce brittle failures for insignificant timing noise.

---

# 45. Startup Strategy

Startup should avoid loading unnecessary systems.

Do not initialize:

- AI providers,
- database connectors,
- plugin systems,
- large indexes,

when they are not used.

The first desktop milestone should start quickly with only required components.

---

# 46. Lazy Initialization

Future expensive subsystems may initialize only when needed.

Examples:

```text
Open Data Workspace
→ initialize data-related services
```

```text
Use Import
→ initialize importer registry
```

```text
Use future database connection
→ initialize database adapter
```

---

# 47. Logging at Scale

Diagnostic logging must be useful without creating excessive I/O.

Avoid:

- logging every mouse movement,
- logging every frame,
- logging every row value,
- logging sensitive imported data.

Use structured, severity-based logging.

---

# 48. Future Local Parallelism

Some deterministic operations may later benefit from parallelism.

Examples:

- validation of independent model sections,
- import parsing,
- indexing,
- expensive layout calculations.

Parallel execution is optional.

Correctness and simplicity come first.

---

# 49. Thread Count

Do not hard-code an excessive number of worker threads.

Use a bounded worker pool appropriate to the machine.

The exact policy is deferred.

ERDFlow should remain usable on modest hardware.

---

# 50. Future Service Scale

If ERDFlow later connects to cloud services, the desktop architecture should not require major domain rewrites.

Potential future service layout:

```text
Clients
   ↓
API / Edge
   ↓
┌───────────────┬────────────────┬───────────────┐
│ Project       │ Collaboration  │ AI Gateway    │
│ Service       │ Service        │               │
└───────────────┴────────────────┴───────────────┘
        │
        ▼
Background Workers
        │
        ▼
Storage / Cache / Observability
```

This is future direction only.

---

# 51. Stateless Service Preference

Future services should be stateless where practical.

State should live in:

- durable storage,
- explicit sessions,
- versioned project data,
- caches.

Stateless services are easier to scale horizontally.

This does not affect the first desktop implementation.

---

# 52. Background Jobs in Future Services

Heavy remote work may eventually use jobs.

Examples:

```text
Large reverse engineering
AI-assisted modeling
Document analysis
Massive imports
Large project conversion
```

Conceptually:

```text
Client request
    ↓
Job created
    ↓
Worker processes
    ↓
Result stored
    ↓
Client retrieves/reviews
```

Not required now.

---

# 53. Horizontal Scaling

Future cloud services should be designed so more service instances can be added.

This may later require:

- stateless APIs,
- shared durable storage,
- distributed queues,
- caches,
- rate limits,
- observability.

No distributed implementation belongs in the desktop milestone.

---

# 54. Future Collaboration Scale

Real-time collaboration is explicitly deferred.

If introduced later, it may require:

- model revisions,
- conflict handling,
- operation history,
- project synchronization,
- permissions,
- presence,
- network resilience.

Current stable IDs and semantic commands help preserve a path toward that future without building collaboration today.

---

# 55. Future AI Scale

AI operations may be:

```text
Local
Cloud
Plugin-provided
Our own service
```

AI must remain behind an adapter.

Large AI workloads should not run on the UI thread.

Future AI requests may use job infrastructure.

AI does not directly mutate the Project.

---

# 56. Future Database Connection Scale

Direct database connections may involve enormous datasets.

ERDFlow should never assume:

```text
Connected database
→ load every table
→ load every row
→ hold everything in RAM
```

Instead:

```text
Metadata on demand
Rows on demand
Query sorting/filtering
Pagination/chunking
Explicit refresh
```

---

# 57. Offline-First Requirement

Scale must not destroy local usability.

Core desktop workflows should remain available offline:

- conceptual modeling,
- relational modeling,
- table design,
- project save/load,
- deterministic conversion,
- SQL generation,
- local imports,
- local data work where applicable.

Future cloud features are additive.

---

# 58. Cross-Platform Performance

Performance should be tested independently on:

```text
macOS
Windows
Linux
```

A solution that performs well only on one platform is not sufficient.

Platform-specific optimizations should be isolated.

---

# 59. Hardware Diversity

ERDFlow should not assume high-end hardware.

Testing should include:

- lower-memory machines,
- older CPUs,
- integrated graphics,
- high-DPI displays,
- different screen sizes.

The application should degrade gracefully.

---

# 60. GPU Usage

Qt may use accelerated rendering depending on the chosen graphics stack.

ERDFlow should not depend on exotic GPU features for correctness.

GPU acceleration may improve presentation performance, but domain and conversion logic remain CPU/core concerns.

Exact rendering backend decisions belong to the Canvas architecture phase.

---

# 61. File Size Limits

Imported files are untrusted and may be extremely large.

ERDFlow should eventually define configurable or reasonable limits.

Examples:

```text
Maximum preview rows
Maximum document depth
Maximum nested JSON depth
Maximum parser memory budget
```

Limits should protect the application from accidental or malicious resource exhaustion.

---

# 62. Bounded Work

Parsing and transformation algorithms should avoid unbounded recursion and uncontrolled allocation.

Especially important for:

- malformed JSON,
- deeply nested structures,
- malicious SQL,
- huge imported strings,
- future document parsing.

---

# 63. Denial-of-Service Protection for Local Input

Even desktop software can be frozen by hostile or malformed files.

Import architecture should include:

- size checks,
- cancellation,
- timeouts where appropriate,
- depth limits,
- memory limits,
- bounded diagnostics.

---

# 64. Database Query Safety

Future live database queries should use:

- pagination,
- bounded result sets by default where appropriate,
- explicit user actions for expensive operations,
- clear warnings for destructive actions.

A Data Grid should not accidentally execute an unlimited expensive query simply because the user opens a table.

---

# 65. Save and Recovery Strategy

Future production releases should consider:

- safe atomic save,
- autosave,
- recovery files,
- crash recovery,
- project backup history.

Only atomic/safe save is required architecturally now.

Autosave behavior is not yet locked.

---

# 66. Telemetry

Telemetry is not required for V1.

If introduced later:

- it must be privacy-aware,
- it must avoid user database contents,
- it should collect only useful operational metrics,
- it should support informed product improvement.

Telemetry does not belong in the Domain.

---

# 67. Observability for Future Services

Future cloud systems may require:

```text
Logs
Metrics
Traces
Health checks
Job metrics
Error rates
Latency
```

This is deferred until cloud services exist.

---

# 68. Scale and Rust

Rust may later improve:

- memory safety,
- parser robustness,
- reusable conversion services,
- concurrent workloads,
- server-side reuse.

But Rust is not a substitute for good architecture.

Poor algorithms remain poor algorithms in Rust.

Scale decisions should be based on profiling and correctness first.

---

# 69. Scale and C++

C++20 remains appropriate for the Qt desktop application.

C++ gives:

- native performance,
- mature Qt integration,
- control over memory/layout,
- broad cross-platform support.

The main risks are complexity, ownership mistakes, and accidental coupling.

Architecture and testing must control those risks.

---

# 70. Performance Budget Philosophy

Before optimizing a feature, define:

```text
What operation?
What input size?
What current measurement?
What acceptable latency?
What user impact?
```

Do not optimize based on intuition alone.

# 72. Responsiveness Rule

Even when an operation takes time, the application should remain interactive where safe.

Users should be able to:

- move the window,
- read status,
- cancel,
- switch to unrelated views when safe,
- understand what is happening.

---

# 73. Partial Results

Some operations may eventually support partial results.

Examples:

```text
Import preview
Search
Large data query
Metadata discovery
```

Partial results are optional and should only be used when correctness remains clear.

---

# 74. Resource Ownership

Resource ownership should be explicit.

Examples:

- who owns a background task,
- who owns a Data Source,
- who owns a conversion snapshot,
- who owns generated candidates,
- who cancels work when a project closes.

Ambiguous ownership causes leaks and concurrency bugs.

Exact C++ ownership types are deferred.

---

# 75. Project Close Behavior

Closing a project while background tasks are running must be safe.

Possible behavior:

```text
Project closing
    ↓
Cancel related tasks
    ↓
Wait/resolve safely
    ↓
Release resources
```

Tasks must not write into destroyed project/UI objects.

---

# 76. Future Multiple-Project Compatibility

Multiple simultaneously open projects are not a current scale requirement.

ERDFlow should simply avoid unnecessary global mutable state that would
make future multi-project support difficult.

No `ProjectSession` architecture or multi-project UI is required now.

This remains a future product possibility rather than a current scale
subsystem.

---

# 77. Project-Scoped Resources

Even with one active project, project-related resources should have clear
ownership.

Examples include:

- undo history,
- background tasks,
- generation baselines,
- mapping/provenance data,
- save state,
- temporary conversion candidates.

The exact ownership container or class is not locked.

The current requirement is only that project-scoped resources do not
become uncontrolled global state.

# 83. Scale Anti-Patterns

Avoid:

1. rebuilding the entire scene for every small edit,
2. full-project validation after every trivial action when not needed,
3. loading entire remote tables into memory,
4. storing duplicate full project copies unnecessarily,
5. unbounded undo history,
6. running heavy tasks on the UI thread,
7. background threads directly mutating Qt widgets,
8. executing imported SQL automatically,
9. choosing distributed architecture before a real need,
10. using “millions of users” as justification for premature complexity.

# 86. Scale Decisions Locked in v0.1

The following are accepted:

1. Desktop performance comes before cloud scale.

2. UI thread must remain responsive.

3. Heavy work must be executable in background tasks.

4. Background tasks should prefer immutable snapshots.

5. Workers must not directly mutate Qt UI objects.

6. Project mutation must remain controlled.

7. Canvas updates should be incremental.

8. Large diagrams should not require full-scene rebuilds for small edits.

9. Validation should support incremental operation where practical.

10. Conversion operates independently of Qt.

11. Mapping lookup must be efficient by stable ID.

12. Generation baselines are used to protect manual work.

13. Undo history must eventually be memory-bounded.

14. Imports should support progress and cancellation.

15. Large imports should support streaming/chunked strategies where practical.

16. Import preview must be bounded.

17. Data Workspace must support paged/chunked data sources.

18. Sorting/filtering may be delegated to remote data sources.

19. Do not load entire future remote tables into memory.

20. Memory usage must be measured.

21. Caching is introduced only with clear invalidation rules.

22. Auto-layout runs outside the UI thread when expensive.

23. Failed background work must not corrupt the Project.

24. Performance must be measured, not assumed.

25. Benchmark fixtures should be maintained.

26. Future services may scale horizontally, but are not implemented now.

27. Offline-first desktop capability must remain intact.

28. Resource limits are required for untrusted imports.

29. Rust is optional and does not replace sound algorithms.

30. Common mapping/provenance and stable-ID lookups must avoid repeated
    full-model scans where indexed lookup is practical.

31. Snapshot creation itself is part of the performance budget.

32. Regeneration peak memory must explicitly account for the coexistence
    of baseline, current model, candidate model, mappings/provenance, and
    undo/change data.

33. Undo limits must consider payload memory, not only command count.

34. Multiple-project architecture is not a current scale requirement.

35. Scale must not be used to justify premature complexity.

# 88. Scale Invariants

## Invariant 1

The UI thread is never intentionally blocked by known heavy work.

## Invariant 2

A small edit should not trigger unnecessary whole-project work.

## Invariant 3

Background work does not mutate Qt widgets directly.

## Invariant 4

Failed work leaves the Project valid.

## Invariant 5

Large external data does not require full in-memory loading by design.

## Invariant 6

Remote Data Grid sorting/filtering can be delegated to the source.

## Invariant 7

Cross-level mappings and stable-ID lookups must support direct/indexed
lookup suitable for large projects.

Common mapping operations must not require repeated full-model scans when
an indexed lookup is practical.

## Invariant 8

Snapshot creation is part of the performance budget and must preserve a
consistent model state.

## Invariant 9

Regeneration memory must account for the possible coexistence of the
baseline, current model, new candidate, mappings/provenance, and undo/change
data.

## Invariant 10

Undo/redo limits must consider payload memory, not only the number of
commands.

## Invariant 11

Performance claims require measurement.

## Invariant 12

Cloud scale does not compromise standalone desktop use.

## Invariant 13

Scale architecture remains proportional to current product needs.

# 89. Summary

ERDFlow should scale in layers.

First:

```text
Smooth local desktop
```

Then:

```text
Large local projects
```

Then:

```text
Large imports and data
```

Then, only when needed:

```text
Connected services
```

And much later, if the product requires it:

```text
Mass-scale ecosystem
```

The scale philosophy is:

> Keep the local experience fast, keep heavy work isolated, measure before optimizing, and preserve clean boundaries for future growth.
