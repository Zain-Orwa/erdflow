> For implemented behavior and remaining work, see [Implementation Status](IMPLEMENTATION_STATUS.md). This document also defines future scope.

## Product Constitution

**Working Product Name:** ERDFlow

**Product Type:** Standalone Visual Database Design Desktop Application

**Core Principle:**

> Draw once, progressively refine.

---

# 1. Product Definition

## 1.1 Product Purpose

ERDFlow is a standalone, professional, cross-platform desktop application
for designing, understanding, refining, transforming, and working with
database models.

The application provides one continuous database-design workflow:

Conceptual ERD
    ↓
Relational Schema
    ↓
Physical / Table Design
    ↓
SQL
    ↓
Data

These stages are different representations of the same underlying
database project.

The user should not need to redraw the same database separately at
every stage.

A user can begin with a high-level conceptual database model and
progressively add more detail until the design becomes an
implementation-ready database.

ERDFlow is desktop-first and should provide a fast, responsive, clean,
professional, intuitive, and native-feeling experience on:

- macOS
- Linux
- Windows

ERDFlow must remain an independent product.

Its architecture should maintain clean boundaries so its database-design
capabilities can potentially be reused as a component of a larger system
in the future without coupling the current product to that system.

---

# 2. Problem Statement

Database design normally progresses through several levels:

Conceptual ERD
    ↓
Relational Schema
    ↓
Physical / Table Design
    ↓
SQL
    ↓
Data

Many existing database-design tools focus strongly on only one or two
of these stages.

For example, one application may be good for Conceptual ERD drawing,
while another is needed for relational schemas, physical table design,
SQL generation, or working with data.

This fragments the database-design process.

Users may need to:

- recreate the same database in multiple tools,
- manually transfer information between stages,
- repeat work when the model changes,
- maintain several disconnected representations,
- manually verify consistency,
- and switch between different applications.

ERDFlow aims to solve this by keeping the database design inside one
project and allowing the same underlying model to progressively evolve
from a conceptual design toward an implementation-ready database.

The goal is not simply:

Conceptual Tool
+
Schema Tool
+
Table Tool
+
SQL Tool
+
Data Tool

The goal is:

One Database Project
        ↓
Conceptual
        ↓
Schema
        ↓
Tables
        ↓
SQL
        ↓
Data

# 4. Product Goals

ERDFlow should:

1. Make conceptual database modeling easy to understand and use.
2. Support professional database-design concepts.
3. Keep different database-design stages connected.
4. Reduce repeated manual work.
5. Support progressive refinement.
6. Perform known database transformations deterministically.
7. Allow users to review and modify generated results.
8. Protect manual work when upstream or downstream models change.
9. Support controlled synchronization between modeling levels when a meaningful equivalent exists.
10. Import existing database information.
11. Generate implementation-ready SQL.
12. Provide a live, spreadsheet-like Data Workspace for viewing, sorting, filtering, searching, and editing rows.
13. Remain responsive with large projects.
14. Work consistently across macOS, Linux, and Windows.
15. Remain fully useful without AI or cloud services.
16. Maintain clean product boundaries so capabilities can be reused later.

## 4.1 System Quality Requirements

ERDFlow must be a sustainable, scalable, secure, maintainable, and usable system.
These qualities guide each development milestone from the initial desktop
foundation onward:

- **Sustainable:** Keep long-term development and operation practical through
  proportionate complexity, documented decisions, deliberate dependency choices,
  and efficient use of resources.
- **Scalable:** Support growing models and datasets while preserving UI
  responsiveness and bounded resource use. Establish limits through measurement
  and benchmarks as described in `4.ERDFlow_SCALE.md`.
- **Secure:** Validate external input, protect project data and credentials,
  and make destructive operations and external writes explicit and controlled.
- **Maintainable:** Keep responsibilities and dependencies clear, preserve a
  Qt-independent domain, test behavior at the appropriate layer, and keep
  documentation consistent with implementation.
- **Usable:** Make workflows understandable, accessible, consistent, and
  responsive, with clear feedback and recoverable mistakes for both learners
  and professional users.

Each milestone should consider these qualities within its actual scope and
record relevant tradeoffs. They do not require implementing future features
before they are needed.

# 7. Progressive Refinement

ERDFlow follows:

> Draw once, progressively refine.

For example, a user may begin with:

Student --- Enrolled --- Course

Then add cardinality:

Student M:M Course

Then add participation:

Student = Total Participation

Course = Partial Participation

Then add attributes to the relationship:

RegistrationDate
Grade
Attempt

Then convert the relationship into an associative entity if required.

The user should not need to delete and rebuild the model at every step.

Existing concepts should become progressively richer.

# 8. Project Structure

One database design should normally exist inside one ERDFlow project.

Working project extension:

.erdx

Example:

university.erdx

A project may contain:

University Project

├── Conceptual ERD
│   ├── Page 1
│   ├── Page 2
│   └── Page 3
│
├── Relational Schema
├── Table Design
├── SQL
└── Data

Large Conceptual ERDs may use multiple pages.

The pages remain part of the same conceptual model.

The project format must be versioned so it can evolve safely over time.

## Pages are not projects

Two different things can be called "several diagrams", and ERDFlow keeps them
apart:

- **Pages** divide one database design across several sheets. They share one
  conceptual model, so an entity drawn on page 1 is the same entity when a
  relationship on page 3 refers to it. Pages live inside a single `.erdx`.
- **Projects** are separate database designs. A university and a hospital have
  nothing to say to each other, and nothing is shared between them.

A folder holds projects. A project holds pages.

## Where projects live

A folder in ERDFlow is a real folder on disk, and a project is a real `.erdx`
file inside it. ERDFlow keeps no library database and owns no location, so:

- Finder and Explorer show exactly what ERDFlow shows.
- Renaming a project in Finder renames it in ERDFlow, because there is only
  one name and it is the file's.
- Projects sync through iCloud, Dropbox or git, travel on a USB stick, and
  survive ERDFlow being uninstalled, with no export step.
- Nothing can go stale, because there is no second record of where a project
  is.

ERDFlow offers a home folder, **ERDFlow Projects** in the user's documents,
and points new projects at it. It never requires it. A project may be saved
anywhere, kept loose under its own name beside unrelated files, or organised
into folders the user makes, and ERDFlow treats all of these the same way.

Searching across many projects may later be made faster with an index. Such an
index is a cache derived from the folders, rebuildable at any time by reading
them again, and never the record of where anything is.

## The start screen

ERDFlow opens on a start screen laid out the way Google Docs and the Office
start screens are: a band of templates across the top, and the user's own
projects filling the rest.

### The template band

Headed **Start a new diagram**, a single horizontal row of cards:

- **Blank** is the first card, always, marked with a plus and nothing else, so
  the shortest path to drawing is one click.
- Each remaining card carries a **thumbnail of the diagram that template
  actually contains**, not a generic icon, so the row is read by eye rather
  than by name.
- Each card is captioned on two lines: the template's name, and beneath it in
  lighter text the notation it is drawn in — `University / Chen`,
  `Orders / Crow's foot`.
- The row ends with **Template gallery**, which opens the full set when more
  templates exist than a row can hold.
- The band **collapses**, and stays collapsed until it is opened again, for a
  user who wants their own projects at the top of the window.

### The project list

Below the band, the projects the user already has, newest first and **grouped
under date headings** — Yesterday, Previous 30 days, Earlier — rather than run
together as one long list.

Each row shows the project's name, the folder it sits in, and when it was last
opened. Controls above the list:

- **Sort**, by last opened, last modified, or name.
- **Folder**, filtering to one folder or showing every project ERDFlow knows
  of.
- **Grid or list**, where grid shows each project as its own thumbnail.
- **Browse**, to open a project anywhere on disk, and a way to open the home
  folder in Finder or Explorer.
- **Search**, over project names.

V1 ships no accounts, so the start screen shows no owner column and no
"shared with me" yet, and the folder is the organising idea in their place.
The slot is reserved rather than argued away: accounts, shared projects and
agents are all intended, as section 50 records, so the project list is
designed to gain an owner and a collaborator column without being rebuilt.

### Thumbnails

A thumbnail is rendered from the project and kept in a cache keyed by the
file's path and modification time, so a folder is drawn quickly after the
first visit and a project that changes is redrawn. The cache is derived and
rebuildable: deleting it costs a redraw and nothing else, which keeps the
folders the only record of what exists. Built-in templates carry their
thumbnails already rendered, since they never change.

If browsing large folders ever feels slow, the alternative is to store a small
thumbnail inside the `.erdx` itself, so it travels with the file and a folder
seen for the first time needs no rendering at all. That is a format change and
is not worth making before the cache has been shown to be too slow.

### Behaviour

A recent entry whose file has moved or been deleted says so plainly and offers
to forget it, rather than failing when it is clicked. Since folders are real,
this happens whenever a user tidies up outside ERDFlow, and it is ordinary
rather than an error.

The start screen is skippable. A user who wants a blank canvas on launch
should be able to say so once and never see it again, and a file passed on the
command line, or `--example`, bypasses it as it already does.

## Templates

A template is a project. There is no template format, no placeholder syntax,
and no second reader to keep correct. **New from template** copies an `.erdx`
and leaves the copy untitled and unsaved, so a template can never be
overwritten by the work started from it.

Two kinds are offered:

- **Worked schemas**, complete diagrams to open, read and adapt: University,
  Library, Hospital, Orders, Employees, Airline and Bank. The existing
  university example becomes the first of these rather than a separate
  feature.
- **Starting frames**, genuinely empty, carrying a title block and a chosen
  notation, so a new diagram begins in the notation its author teaches or is
  taught in.

Built-in templates are embedded in the application the way the icon sets are,
so ERDFlow has no content it can be started without. **Save as template**
writes an `.erdx` into a templates folder inside the home folder, and anything
found there appears in the gallery beside the built-in ones.

# 11. Relationship Cardinality Rule

Relationship ratios must appear near the entity to which they belong.

Correct:

[Customer]  1 ---- ◇ Subscribe ◇ ---- M  [Mobile]

The `1` belongs visually near Customer.

The `M` belongs visually near Mobile.

ERDFlow should support:

1:1

1:M

M:1

M:M

The labels must not float randomly in the middle of the connector.

This is a required visual behavior of ERDFlow.

# 12. One Conceptual Model

The Conceptual ERD is **one model**. ERDFlow does not maintain a Basic model
and a Convertible model, and there is no mode a project is in.

The underlying data is the same whether a beginner or a professional database
designer is drawing it. What a student draws and what an engineer converts are
the same entities, the same attributes and the same relationships, stored the
same way.

The difference between the two audiences belongs in the **user interface**, not
in the project model:

```text
Properties
├── Name
├── Description
└── For the schema          ← collapsible
    ├── Logical type
    ├── Length
    ├── Identifier
    ├── Required
    ├── Unique
    └── Comment
```

A beginner may keep the section closed. An advanced user may keep it open.

Whether it is open or closed is a **user preference**. It is not semantic
project data, it is not written into the project file, and two people working
in one project may hold it differently.

> **Rule**
>
> View preferences belong to the user.
> Semantic database information belongs to the project.

This replaces the earlier Basic / Convertible mode design. A project file no
longer records a mode, and no information is hidden from conversion because of
how someone has arranged their panel.

# 22. Comments and Descriptions

ERDFlow has two things that could both be called a comment, and they are
different features that must not be conflated. See
[ADR-017](adr/ADR-017-REVIEW-COMMENTS.md) for the reasoning.

- A **description**, below, documents the model. It says what a Student *is*,
  it is part of what the model means, and it travels forward into the
  Relational Schema and out into generated SQL. The "For the schema" section
  adds a structured comment field beside the logical type for the same purpose.
- A **review comment** is about the work rather than part of it — "should this
  be weak?", "check this with Dana". It is pinned to elements, to the lines
  between them, or to a range of somebody's writing; one remark may be pinned
  to several things at once; it appears when what it is pinned to is pointed
  at; and it can be put away without being deleted. It never reaches the
  schema, because it is not part of the model. This is implemented.

Neither is the **Note**, which is a card placed on the canvas and is part of
the drawing.

## Descriptions

Users should be able to store comments or descriptions on:

- Entities
- Attributes
- Relationships
- Schema Relations
- Tables
- Columns

Example:

Entity: Student

Comment: Represents a registered university student.

Comments should remain attached to the semantic database model and, where applicable, travel forward into later stages.

# 24. Conversion Readiness

## Validation and readiness are different systems

ERDFlow asks two different questions about a project, and keeps them apart:

```text
validate(project)   →  Is the project structurally and semantically valid?
readiness(project)  →  Is this valid model ready to be converted?
```

A validation problem is a broken model: a reference to a deleted object, an
impossible weak-entity structure, a violated domain invariant. A readiness
problem is a sound model that has not yet answered a question conversion needs
answered: an entity with no identifier, an attribute with no logical type, an
ISA whose mapping strategy has not been chosen, an M:M whose junction relation
has not been named.

> **Rule**
>
> Validation ≠ Conversion Readiness.

A model may be perfectly valid and not yet ready. Saving an incomplete but
structurally valid model remains allowed. The accepted
[validation policy](adr/ADR-009-VALIDATION-GATES-AND-CONVERSION-POLICY.md)
defines the separate save and conversion gates.

## Readiness issue classes

Not every unresolved item is an error. Readiness reports what kind of thing
each issue is:

- Domain invariant violation
- Blocking conversion error
- Non-blocking warning
- Advisory information
- Unresolved conversion decision

Examples:

```text
Weak entity without identifying relationship   →  Blocking conversion error
Entity without chosen identifier               →  Unresolved conversion decision
Missing optional description                   →  Advisory information
```

## Readiness is a navigable report, not a wizard

ERDFlow must not answer Convert with one large dialog asking dozens of
questions. It shows a structured list:

```text
Conversion Readiness

3 Blockers
2 Warnings

[Student]              No identifier selected
[Person Specialization] ISA mapping strategy unresolved
[Enrolled]             Junction relation name unresolved
[Employee.name]        Logical type missing
```

Every issue is clickable, and clicking one:

1. navigates to the element,
2. selects it on the diagram,
3. opens and focuses its Properties panel,
4. highlights the field that needs attention.

> **Rule**
>
> Readiness guides the user back to the real model rather than duplicating the
> model inside a conversion wizard.

Small focused dialogs are reserved for decisions that are a genuine structural
choice — an ISA mapping strategy is the clearest example. They are not used for
data the Properties panel can already collect.

## Readiness percentage

The UI may derive a figure such as `Schema Readiness: 87%`. The percentage is
presentation. It cannot override or conceal a blocker, and the core's
authoritative answer is always the structured list of issues.

## Conversion decisions persist

Once the user answers a conversion question, ERDFlow remembers the answer. It
is tied to the element's stable identity, not to a position or a name:

```text
EntityId           →  identifier / surrogate-key decision
AttributeId        →  what a composite becomes: Parts, Whole or Both
SpecializationId   →  ISA mapping strategy
RelationshipId     →  junction relation name, and which side of a 1:1 takes the key
Project            →  naming convention, FK convention, surrogate policy
```

A composite attribute has three answers, and the default is the textbook one:

- **Parts** — `Name` becomes `First`, `Mid`, `Last`. Atomic values, which is what
  first normal form asks for.
- **Whole** — one `Name` column; the parts are not stored.
- **Both** — the parts are stored, and `Name` is a generated column computed
  from them. A value computed rather than stored is what a derived attribute
  already is, so this needs no new concept.

> **Rule**
>
> Do not ask the same resolved conversion question every time the user
> converts.

Because the decisions are part of the project rather than part of a dialog,
they are also editable from the Properties panel, and a later conversion reuses
them instead of re-asking.

## Defaults must not become decisions

A value the editor uses because nothing else was said is not the same as a
value the user chose. A relationship side that defaults to `M` / `Partial` must
not be read as a deliberate choice of `M` / `Partial`, or conversion will build
junction relations out of questions nobody was asked.

Confirmation is therefore tracked beside the value:

```text
Participant
├── cardinality
├── cardinality_confirmed
├── participation
└── participation_confirmed
```

> **Rule**
>
> A default used by the UI must not silently become semantic truth.

# 25. Conceptual to Relational Schema Conversion

When the Conceptual model is sufficiently defined, the user should be able to choose:

Convert → Relational Schema

Known database transformations should be deterministic.

Examples:

Strong Entity → Relation

1:M → Foreign Key on the M side

M:M → Junction Relation

Multivalued Attribute → Separate Relation

Associative Entity → Relation

Weak Entity → Owner key combined with weak-entity identification

Generalization / Specialization → Selected relational mapping strategy

Known database rules should not require AI.

## The conversion pipeline

```text
Conceptual Model
        ↓
Validation
        ↓
Readiness
        ↓
Resolve blockers / decisions
        ↓
Generate Candidate
        ↓
Preview
        ↓
Compare with shared downstream state
        ↓
Three-way review where necessary
        ↓
Apply to Shared Schema      ← authorization required here
        ↓
Domain update
```

## Generating and previewing a candidate is free

Converting produces a **candidate**. A candidate changes nothing that anyone
else can see, so producing one needs no special authority. Any participant who
may read the project may convert it, look at the result, and compare it with
what already exists.

This holds at every legitimate level of participation — a viewer, a commenter,
an editor, a guest, a custom role, and an AI agent with project-read access.

Preview means inspecting the project, generating safe candidate
representations, inspecting potential conversions, and inspecting differences
and proposed changes. Preview never replaces the shared schema, never changes
shared project truth, never deletes data and never bypasses a permission.

> **Rule**
>
> Authorized participants may evaluate the consequences of a change without
> receiving permission to apply that change.

## Applying to the shared schema is the protected step

The operation that needs authority is the one that changes what everybody else
sees:

```text
Generate Candidate → Preview → Review differences → Apply to Shared Schema
                                                            ↓
                                                   Authorization check
                                                    ├── Yes → Apply
                                                    └── No  → Request permission
```

> **Rule**
>
> Permission protects shared truth, not harmless candidate generation.

A request for permission must not freeze the person who made it. They keep
working, and they keep their candidate.

## How the schema is drawn

The preview is a picture of the schema, not a list of it, and it is drawn the
way relational schemas are drawn.

**Lines are straight, with right-angle deflections.** They never curve. A curve
cannot be followed with the eye across a busy schema, and a reader who loses a
line has lost the relationship it was drawing.

**Lines join the exact rows they concern.** A foreign key is joined to the
primary key it references, and the line meets each table at the vertical
position of that row rather than at the table's edge or its middle. Anything
else leaves the reader unable to tell which column is involved. A recursive
relationship is drawn the same way, leaving a table's foreign-key row and
returning to its own primary-key row.

This is also the default when a user draws a link by hand: dragging a connector
between two tables lands on the primary key and the foreign key, taken from what
the Conceptual diagram already says. The user may move it afterwards, but the
default arrives correct rather than needing to be aimed.

**The schema carries its own controls**, above the tables, in two menus rather
than a row of eight pickers — grouped by the question they answer:

- **Arrange** — Align to the grid, Tidy, Release the lines (which gives every
  line back to the router while leaving the tables exactly where they are),
  whether lines are found around the tables or taken straight there, and
  whether a line shaped by hand moves out of the way of a table dropped on it.
- **Appearance** — the notation, and whether tables are named plural or as the
  diagram draws them.

A row that names every setting at once is a row nobody reads. They sit above the
schema because they are what a reader changes while looking at it.

**Given the whole window, the schema is given the whole window.** The ribbon and
every tool row go away with the diagram they draw on: a row of shapes to place,
above a canvas nobody can currently see, is a row of things that cannot be done.
What is still worth reaching for comes out in the header instead — Undo, Redo, a
search of the schema, and the theme. The diagram's own search goes too, since
the diagram is not what is on screen.

**The line ends carry a notation the user chooses**, crow's foot among them.
These are the same cardinality notations the Conceptual editor draws, reused
rather than reimplemented. The choice is one choice: picking a notation changes
the diagram and the schema together, because they are two views of one model and
a reader should never have to hold two notations in mind at once.

**No two lines are laid along each other.** A line finds its own way between the
tables rather than through them, and where several leave the same side of a
table they turn at different distances out, so their long runs lie beside one
another instead of on top. Where several foreign keys point at one primary key —
which is the ordinary case, not the exception — they are fanned across the row
they land on so that their end symbols can still be told apart.

**A line can be moved, and so can each of its ends.** Every part of a connector
answers to the hand:

- **Any straight run** can be pushed sideways, taken hold of anywhere along it.
  The whole run moves and keeps its length; the runs either side stretch to
  follow. An upright run moves across, a level one up and down, and the cursor
  says which before it is grabbed. A run cannot be pushed along its own length,
  because that would move nothing.
- **Either end** can be taken hold of and moved anywhere around the outline of
  the table it joins — down a side, along the top, round to the other edge. The
  automatic join is a starting point, not a fixture. **The whole line follows
  it**, the way a rope follows the end that is pulled: the path is found again
  from wherever the end now is, for every step of the drag, rather than the
  line holding its old shape and stretching at one corner to reach. Moving an
  end therefore gives up whatever route the line was keeping, which is the
  price of the line following properly.
- **Double-clicking** the line gives the whole of it back to the router, and
  Tidy returns every line and every table at once.

> **Rule**
>
> A line is pushed, never pinned through.

**The symbols at an end belong to the line.** The crow's foot, the "one" bar,
the minimum tick and the Chen label are drawn along the line from its end, so
the line has to run straight for at least as far as they reach. A run pushed
right up against a table would turn out from under them and leave them standing
in open space beside a line that has walked off without them. It is therefore
held: a run cannot be pushed nearer an end than the symbols there need, and the
turn stops rather than the symbols coming adrift. The join is never moved to
achieve this — the turn is held off, not the line pulled away — and the end
itself stays as freely draggable as ever.

Dropping a single point into the middle of a straight length and routing the
line through it is the wrong model, and looks it: the line detours out to the
point and back, drawing a spur where the reader asked for a line that had moved
aside. So a run is moved as a run. The first push also settles the route — until
then the path is worked out afresh each time, and a run cannot be moved out of a
shape that is about to be recalculated — so from that moment the line keeps the
route it has, and only its two ends still follow their tables, with the run
beside each end stretching to keep up.

A line is drawn behind the tables, so a schema is never crossed out by its own
connections — except the one under the pointer, which is drawn over them so that
what is being worked on can be followed for its whole length. Because it is
drawn on top there, it can be taken hold of there: a line always answers the
pointer before the table it happens to cross.

**An end pulled off its table stays where it was let go.** It does not spring
back to the edge, because an end that springs back cannot be aimed, and a reader
moving a connector out of the way is doing something deliberate.

> **Rule**
>
> Nothing the hand places is quietly undone.

**Moving one table moves one table.** Every other table stays exactly where it
was. This is only true because the automatic arrangement is worked out for all
of them and a table placed by hand simply sits somewhere else instead: leave a
moved table out of the packing and the ones after it shuffle up into the space
it left, so moving one table appears to move several.

**A line shaped by hand keeps its shape when a table is moved onto it** — by
default. A shape somebody made is theirs, and a line that undid itself because
a table drifted over it would be undoing their work for a reason they never
asked about. Where that is not wanted, **Move out of the way of tables** in the
Arrange menu hands any line a move has left lying across a table back to the
router, which takes it around. It is handed back in the same edit as the move
that displaced it, so one undo takes both back together.

**A table is pulled about by its edges.** Every one of the four is a handle,
and so is every corner: take hold of the side you want to move and it follows
the pointer, while the side opposite it stays exactly where it was. Pulling the
left edge therefore widens the table leftwards rather than dragging the whole
thing sideways, and the table is put where its corner ended up in the same edit
as the size, so one undo takes both back together. A corner pulls the two sides
that meet at it. The width runs between what a column of keys needs and what an
eye can still follow across; a line always answers the pointer before the table
it crosses, so where a line lies along an edge, the table is taken hold of
further along it.

**Room given to a table's height is shared out between its rows.** A table is
its rows, so a taller table is a roomier one rather than one with a gap under
its last row, and a table can never be pulled shorter than the rows it holds —
nor shorter than the questions it is still asking underneath them, which keep
the size they need. A table that gains a column afterwards grows past the
height it was given rather than hiding the new row. **Arrange → Table size**
offers *Resizable*, which is how it starts, and *Fixed*, which takes every
handle away so an edge cannot be caught while a table is being moved.

Resizing a table does not move its neighbours, for the same reason moving one
does not: the arrangement is worked out once for all of them, from the size
each table would have had anyway rather than the size a hand gave it. A table
pulled wide or tall enough may therefore reach over the one beside it or below
it, and moving either of them apart is the answer. The alternative — reflowing
the schema every time a table changes size — is the behaviour this rule exists
to prevent.

> **Rule**
>
> Moving one thing moves one thing.

**Arranging the schema is work, so it is kept like work.** Where a table sits,
the route a line takes and where its ends are put all live in the project
beside the diagram's own layout. They **undo and redo** like any other edit,
and they are **saved** with the document. One drag is one step of history —
the table or line follows the pointer freely and the model is told once, when
the hand lets go, so undo walks back a move rather than a pixel of one.

Wherever a line ends, its end symbols are squared on the line as it was
actually drawn rather than on the side of the table the route set out from. A
line that has been pushed about, or one whose end has been taken off its table,
can arrive from any direction, and a crow's foot lying across a line instead of
along it is the plainest sign that a drawing has stopped describing itself. An
end left off its table stops exactly there, with nothing drawn beyond it.

The foreign key is untouched by any of this: where a line is drawn and what the
model holds are different questions. What changes is that the connection is now
visibly hanging, and the schema says so — the panel reports how many ends are
not connected, beside the count of types still open. It is not an error, nothing
is refused for it, and the project still saves. It is reported because a reader
who has left a connection hanging should be told rather than have the schema
pretend it is joined. Putting the end back on its table clears it.

## Asking the schema a question

**Pressing a table asks what it touches.** The table is outlined, **and the
outline runs out along every line it is joined by** — a table picked out while
its connections look like every other line says only where the table is, when
what was asked was what it reaches. Everything it is joined to stays as it was,
and the rest of the schema fades — one step out in
both directions, because a key is a two-ended fact and the reader means both
ends of it. While a table is being asked about, its foreign-key rows spell out
where they lead (`→ Students.StudentID`) instead of showing a type. Pressing the
bare canvas puts the whole schema back.

**The search in the header asks for a name.** It picks out the tables and
columns whose names carry what is typed and fades the rest. It is a search of
the schema and not of the diagram: the two are looked at separately, and their
names do not always agree, since a table is named for the many rows it holds
and a bridge is named for the relationship behind it.

**The chips above the schema ask about a kind of table** — everything, or only
what came from entities, from relationships, or from attributes. These are the
same four questions the diagram's own search asks, carried across rather than
reinvented. Asking about a kind puts down whichever table was being asked about,
since it is a broader question that would otherwise be answered over the top of
a narrower one. Nothing is removed, only faded, so the schema keeps its shape
and no line is left hanging from a table that is not there.

**Every table says where it came from**, in its header: `ENTITY PERSON`,
`ISA SUBTYPE OF PERSON`, `BRIDGE FOR M:M ENROLLED`, `MULTIVALUED PHONE`. A
reader learning the mapping rules needs to know that Enrolleds is a bridge and
Phones is a multivalued attribute, and the schema is the only place that says
so.

**A type nobody has given yet is drawn as a blank to be filled in** — a dashed
outline round a pane of the warning colour, with the question mark in the middle
of it. A bare `?` at the end of a row reads as a remark about the column; a box
waiting to be filled reads as something to do, which is what it is.

**Pressing that blank opens every type there is.** A line to search by, and
under it the whole SQL Server catalogue in one run — from the type reached for
constantly to the one hardly reached for at all:

```text
int  varchar  nvarchar  bit  datetime2  date  decimal  bigint
uniqueidentifier  nvarchar(max)  varchar(max)  char  nchar  smallint
money  float  tinyint  time  datetimeoffset  datetime  numeric
varbinary  varbinary(max)  real  smalldatetime  smallmoney  binary
xml  rowversion  text  ntext  image  hierarchyid  sql_variant
geography  geometry  cursor  table
```

The list is **not grouped and carries no headings**. A reader looking for a
type is looking for a name, and families only put something between them and
it; the order is the list's whole argument. Typing narrows it without
disturbing that order, the arrows walk it from the search line, and Return
takes the one in hand.

**The highlight follows the pointer.** There is one highlight, and the mouse
and the keyboard both move it, so what a click would take and what Return would
take are never two different things. A highlight that stayed where the keyboard
left it while the pointer wandered would be saying two things at once. The three types SQL Server is removing — `text`, `ntext`
and `image` — are still offered and still open and save, and say what to prefer
instead.

**A type that is measured grows a second cell for its size.** The type sits in
a box of its own and the number sits beside it, because they are two answers
and not one:

```text
PersonID   ( int )
First      ( varchar )   ( 100 )
Last       ( ?       )
```

Both cells are drawn in the **quieter ink**, so a row reads as one thing and
its description rather than as two halves of equal weight. What the column is
called is the row's subject; what it is made of answers a question about it.

Pressing the size asks for it in the terms that type is actually measured in —
characters for a `varchar`, bytes for a `varbinary`, digits after the second
for a `datetime2`, mantissa bits for a `float` — with the values that type
usually takes offered under the field. **The field takes any number**, not only
the ones offered: the list is a convenience and never the whole of what can be
said. A number typed and then clicked away from counts the same as one finished
with Return, because a number written into a field is an answer either way;
opening the field and saying nothing changes nothing. A `decimal` is asked for its scale
alongside its precision; everything else is not asked for a scale it has no use
for. A size nobody has given yet shows what it wants rather than a number, so a
blank size never reads as a real one.

**While a cell is being answered it becomes an empty slot.** The dashes and the
question mark go, and what is left is a plain grey hollow with something open
over it waiting to be put in. The question has been asked; a cell still asking
it would be saying so twice.

**A box means it can be pressed.** A column the conversion invented — a
generated key, a discriminator, a foreign key that takes the type of what it
points at — is written as plain words instead, because none of it is the
reader's to change.

Choosing answers that column where it stands, rather than sending the reader to
the Properties panel for something the schema is already showing them a blank
for. It is an ordinary edit and it undoes. A column that exists only on the
schema is answered the same way, since otherwise it could never stop being a
question.

Nothing that cannot carry an answer ever asks: a foreign key takes the type of
what it points at, a generated key and a discriminator are the conversion's
own, and an ignored column became nothing at all.

**What the conversion left out is listed too.** A derived attribute becomes no
column, and is shown saying `ignored` rather than quietly left out. It holds no
type question, takes no key, and is counted by nothing.

## The questions a conversion cannot answer

Some of what a conversion needs has no single right answer, and ERDFlow will not
guess quietly. Those questions are asked **on the tables they are about**, under
the columns, rather than gathered into a dialog — the model is edited where the
model is:

```text
Persons      ISA mapping strategy:
             (Table per subclass)  ( Single table )  (Table per concrete)

Students     Name is composite. What it becomes:
             ( Parts )  ( Whole )  ( Both )

Courses      Teaches is 1:1, so this key could sit on either table:
             ( On Course )  ( On Professor )
```

The questions are **set apart from the columns**, not listed among them. They
have their own ground below the last column, with a rule between, and the key
gutter stops where the columns stop — a question about the whole table reading
as though it were another row of it is the one way this could mislead.

The answer in force is filled in and named in bold, so which one is in force is
never in doubt. Where it is only what the conversion does because nobody has
said, it is filled **faintly** instead of solid — a default is not a decision,
and the two must not be the same picture. Answering is an ordinary edit: it
undoes, it saves, and it is never asked again.

All three hierarchy strategies are real. Table per subclass gives each child a
table keyed to its parent; single table folds the children into the parent with
a discriminator, and a column belonging to only some rows stops being required
because the other rows have nothing to put there; table per concrete drops the
parent table and gives each child its columns. Whichever is in force, the
question is still asked somewhere, so the answer that removed a table can always
be taken back.

## Answering a repeated name once

Seventeen types open is almost never seventeen questions. It is `ID` asked six
times and `Name` asked five. The strip under the schema gathers the columns that
share a name and lets one answer serve all of them, in a single edit that a
single undo takes back.

> **Rule**
>
> Ask once for what is asked once.

## Naming a key after the role it plays

Where two links join the same pair of tables, the role each side was given names
the key it carries. A flight's departure and arrival airports become
`DepartureAirportID` and `ArrivalAirportID`, not `AirportID` and a qualified
guess at the second — which would say which table the key points at, and nothing
about which of the two it is.

## Editing the schema

A table in the schema can be edited where it is drawn. Right-clicking it offers
to add a column; right-clicking one of its columns offers to remove it.

What may be removed is deliberately narrow. A column the conversion invented —
a bridge's own key, a surrogate, a discriminator — is there because the shape of
the model put it there, and removing it would be arguing with the conversion
rather than editing the model. A foreign key is there because a relationship is,
and it goes when that relationship goes. What is left is exactly what a reader
put there: the diagram's own attributes, and the columns they added here.

### Every edit asks before it touches the diagram

Adding or removing a column may or may not mean the same change to the diagram,
and ERDFlow never decides that by itself. Following
[ADR-010](adr/ADR-010-CHANGE-PROPAGATION-AND-REGENERATION.md) §39–48, the edit is
classified, explained, and put to the user before anything upstream is touched:

```text
Add "Nickname" to the diagram as well?

  Add to both    the diagram gains an attribute of that name
  Schema only    the column stays here; the diagram is untouched
  Cancel
```

**Add to both** is the default, because it is nearly always the answer. It needs
nothing of the schema's own: it is an attribute on the model, and the schema
follows because it is derived from it. Removing from both deletes the attribute,
and undoes like any other edit.

**Schema only** records a difference instead. A column added there exists on the
schema and nowhere else; an attribute removed there stays on the diagram and
stops being drawn as a column. Neither touches the diagram.

> **Rule**
>
> Nothing reaches the diagram without being asked for.

### Divergence is a fact, not a fault

The conceptual model and the relational schema describe different levels, and
are not required to agree. A difference between them is therefore recorded
rather than corrected: it is saved with the project, it survives being reopened,
and it undoes like anything else.

It is also visible. A column that exists here and not on the diagram is named in
italic, and the panel says how many changes are not on the diagram, beside the
count of types still open. That is the whole point of allowing the two to
differ — the difference was meant, so the reader should be able to see it.

These differences are kept apart from the conversion decisions, which answer
questions the conversion cannot settle for itself. A decision has no wrong
answer; these are somebody editing the conversion's result, which is a different
kind of fact. When the Relational Schema workspace arrives they become real
relational objects with identities of their own, and the decisions stay where
they are.

## The diagram's colours travel with it

Nothing the user has done on the diagram is lost when the same project is seen
as a schema.

- A **table's border and the divider lines between its rows** take the colour of
  the entity the table came from.
- A **column row** takes the colour of the attribute it came from.

So one table can carry its entity's colour around the edge while its rows carry
their own attributes' colours, and both are recognisable from the diagram that
produced them. Colours are looked up by the conceptual element a table or column
came from, so the schema invents no palette of its own.

The controls that narrow the diagram — showing only entities, only
relationships, only attributes or only hierarchies, pulling in what a match
touches, and either fading or hiding the rest — work on the schema too.

## Re-conversion never silently destroys manual work

A generated Relational Schema may be edited by hand afterwards, so a later
conversion cannot simply regenerate over it. ERDFlow compares the previous
generated baseline, the current user-edited model and the new candidate, and
produces a reviewable change proposal.
[ADR-010](adr/ADR-010-CHANGE-PROPAGATION-AND-REGENERATION.md) specifies this in
full.

> **Rule**
>
> Generated ≠ disposable.

# 27. Change, Diff, and Controlled Synchronization

The Conceptual model and Relational Schema are connected representations of the same database project, but they are not identical levels.

Changes may originate from either level.

ERDFlow must protect user modifications and must not silently overwrite one level because another level changed.

## 27.1 Conceptual → Schema

Example:

1. The user creates a Conceptual ERD.
2. ERDFlow generates the Relational Schema.
3. The user manually modifies the Schema.
4. Later, the user adds DateOfBirth to Student in the Conceptual model.

ERDFlow should detect the difference and show something similar to:

Conceptual model changed.

Schema differences:

+ Student.DateOfBirth

[ Review Changes ]
[ Apply ]
[ Ignore ]

Applying the change must preserve unrelated manual Schema modifications.

## 27.2 Schema → Conceptual

When the user modifies the Relational Schema, ERDFlow should determine whether the modification has a meaningful equivalent in the Conceptual model.

Example:

Schema change:

Student.Name
→ Student.FullName

ERDFlow should ask something similar to:

This modification can also be represented in the Conceptual model.

Do you want this modification to appear in the Conceptual ERD too?

[ Yes ]
[ No ]

If the user chooses Yes:

1. ERDFlow applies the Schema modification.
2. ERDFlow updates the corresponding Conceptual element.
3. Both views remain synchronized for that change.

If the user chooses No:

1. ERDFlow applies the Schema modification.
2. The modification remains only in the Relational Schema.

## 27.3 Synchronization Boundary

Not every Relational Schema change belongs in the Conceptual model.

Implementation-oriented or technical changes may belong only to the Schema or Physical model.

Examples may include:

- technical foreign-key attributes,
- surrogate keys introduced only for implementation reasons,
- implementation-only helper attributes,
- indexes,
- database-specific constraints,
- physical data-type decisions.

ERDFlow should offer upstream synchronization only when a valid semantic equivalent exists at the higher modeling level.

If the relationship between the two levels is ambiguous, the user should review the change rather than ERDFlow guessing.

The synchronization principle is:

> Detect → Explain → Ask → Apply

ERDFlow must not silently synchronize destructive, ambiguous, or meaning-changing modifications.

Student

|-----------|-------|------------------|
| 1         | Anna  | 2026-08-30 10:15 |
| 2         | Ahmed | 2026-08-30 09:40 |
| 3         | Maria | 2026-08-30 11:05 |

The Live Data Grid should support:

- Edit Row
- Delete Row
- Sort by a selected column
- Sort ascending
- Sort descending
- Filter
- Search
- Refresh
- Import
- Export
- Validation against table constraints

A user should be able to sort the visible rows by any sortable column.

For example, if the table contains a `CreatedAt` column, the user may sort the rows from oldest to newest or newest to oldest.

Example:

Sort: CreatedAt ↓

| StudentID | Name  | CreatedAt        |

# 38. Export

ERDFlow should support useful project and presentation exports.

Export answers two questions that do not have the same answer:

- Can anyone **open** this? That is a picture. Every system reads one, and no
  system can edit it back into a model.
- Can another **tool** read this? That is a model, and only a documented
  format carries one.

Chen conceptual notation has no interchange format. Mermaid ER, DBML,
PlantUML and SQL DDL are all relational, and none of them can express
attribute ovals, ISA triangles, composite, multivalued or derived attributes,
or associative entities. A conceptual diagram therefore travels as a picture
or as `.erdx`, and tool-to-tool interchange begins at the relational level.
ERDFlow should not offer a conceptual export that silently drops the notation
it exists to draw.

## Pictures

Vector, where the diagram stays sharp at any size:

- Current Diagram → SVG
- Current Diagram → PDF
- Project / Diagrams → PDF, one diagram per page

Raster, where the diagram becomes pixels:

- Current Diagram → PNG
- Current Diagram → JPEG
- Current Diagram → WebP
- Current Diagram → TIFF

SVG is the picture to prefer. Its text stays selectable and searchable, the
diagram scales to any size without being redrawn, and every browser, office
suite and design tool opens it. PNG is the default raster: lossless, with
transparency, and accepted everywhere. JPEG, WebP and TIFF exist because a
destination sometimes insists on one, not because a diagram is better in
them — JPEG in particular smears the edges of text and lines, and should
carry that warning where it is offered.

The clipboard is a destination too. **Copy as picture** should put the
selection on the clipboard as both PNG and SVG, so a paste into a document
takes whichever the receiving application prefers.

### The options matter more than the format list

A longer list of formats is worth less than getting a few options right, and
these are the ones that decide whether an exported picture is usable:

- **Resolution.** A raster export needs a scale or a DPI, not just a file
  name. A PNG written at screen resolution looks broken in print; 300 DPI is
  the figure coursework and journals ask for.
- **Extent.** Whole diagram, current selection, or exactly what the view is
  showing. These are three different pictures and a user means a specific one.
- **Background.** Transparent, the theme's canvas colour, or plain white.
  A transparent PNG dropped on a dark slide is the common case that
  fails when the choice is not offered.
- **Margins**, so the diagram is not cropped flush against its own edge.

Every format ERDFlow writes must stay correct for as long as ERDFlow exists,
so a format earns its place by a destination that needs it, not by making the
list longer.

## The export that is also a project

The default SVG carries the project inside it, in a `metadata` element that
every other SVG reader ignores. PNG carries the same payload in a `tEXt`
chunk, which every PNG reader likewise ignores. One file is therefore both
the picture a recipient can open and the project ERDFlow can reopen without
loss. A recipient without ERDFlow sees a diagram; a recipient with it opens
the model.

SVG and PNG are the two that carry it, because they are the two people
actually pass around. The lossy and niche formats carry nothing: a JPEG,
WebP or TIFF export is a picture and says so.

Nothing about the picture depends on the payload. Stripping the metadata
leaves a valid diagram, and an SVG or PNG that ERDFlow did not write is still
accepted as a picture. The embedded project is the same bytes `.erdx` holds
at the same version, so one reader serves both and there is no second format
to keep correct.

A project may hold placed pictures and a background picture, so the embedded
payload is not always small. The export must apply the same 8 MiB limit the
project format applies, and when a project exceeds it the export should write
the picture without the payload and say plainly that it did, rather than
failing or writing a file that cannot be reopened.

## Models

- Project → `.erdx`, the native format, lossless and round-tripping.
- A published JSON Schema for `.erdx`, so a third party can write a reader
  without reading ERDFlow's source.

## Relational exports

Available once the Relational Schema workspace exists, and not before:

- Schema → `.sql`
- Schema → Mermaid ER
- Schema → DBML

Each is one-way and lossy, and says so where it is offered. ERDFlow does not
claim to re-import what it did not write.

## Documentation exports

A diagram is often wanted as a written listing rather than a picture:

- Project → HTML report, one self-contained page carrying the diagram as
  inline SVG above a data dictionary of entities, attributes and
  relationships.
- Project → Markdown data dictionary, for a repository README.
- Entities and attributes → CSV, for a spreadsheet.

These read the model that already exists and need no conversion, so they are
cheap. They are listings, not interchange: nothing re-imports them.

## Formats deliberately left for later

Named so the list is a decision rather than an oversight:

- **EPS**, which some journals and LaTeX workflows still require.
- **EMF**, which pastes into Office on Windows as editable vector rather than
  as a picture. Qt's support is weak off Windows, so it is a platform-specific
  feature or nothing.
- **DOCX and PPTX** embedding, where ERDFlow writes the document rather than
  the picture the user places into one.

## What makes a file readable everywhere

An exported file should carry nothing that ties it to the machine that wrote
it:

- UTF-8 throughout, with no byte-order mark.
- LF line endings in every text format.
- No absolute paths, machine names or user names anywhere in the contents.
- Images embedded rather than referenced, so a file has no sidecar
  dependencies and no link that can break in transit.
- One file, never a directory bundle, so it survives mail, chat and upload
  forms unchanged.
- Keys written in a stable order, so successive saves of the same project
  differ only where the project differs and the format reads usefully in
  version control.

Fonts are the one thing an SVG cannot carry cheaply. Text should name a
generic family with a documented fallback chain so a diagram stays legible on
a machine without the font, and an **outline text** option should be offered
for handoff that must be pixel-exact, trading selectable text for identical
rendering everywhere.

Additional export formats may be added later.

16. AI is optional.
17. AI proposes; the user decides.
18. Visual decoration must remain separate from semantic database data.
19. Desktop experience comes first.
20. The product must remain cross-platform.

22. Do not expand ERDFlow into an ERP product.
23. Design the product so future growth remains possible without over-engineering future features today.

# 49. Product Success Definition

ERDFlow succeeds when a user can begin with an idea for a database, represent it visually, progressively refine it, convert it into a relational design, define its physical implementation, generate SQL, and work with its data without repeatedly rebuilding the same database in disconnected applications.

A user should be able to intentionally propagate meaningful changes between the Conceptual model and the Relational Schema when appropriate, without losing control over implementation-specific differences.

   ↓
Implementation
   ↓
SQL

That flow is the core identity of ERDFlow.

# 50. Accounts, Collaboration and Agents

None of this is built in V1, and all of it is intended. It is recorded here so
that decisions taken now leave room for it rather than having to be undone.

## Accounts

ERDFlow will have user accounts. A project therefore has an owner, and
identity is a real concept in the product rather than something the desktop
application assumes away. Local-first operation remains available: an account
is how work is shared and carried between machines, not a condition of
drawing a diagram.

## Several people in one project

Several people will be able to work in one project together. Phase 57 already
names shared projects, comments, presence, revisions, conflict handling and
permissions, and the stable IDs and semantic commands built early are what
keep that reachable.

## Several agents

Several AI agents will be able to work at once, in every combination of the
three axes, which vary independently:

| Account | Project | Agents |
| --- | --- | --- |
| one | one | several agents in the same project |
| one | several | agents working across a user's projects |
| several | several | agents under different accounts and projects |

This extends the rule that AI control is provider-agnostic and drives the
application through the Editor's own commands rather than through a vendor's
API. Because several people and several agents will issue those commands at
the same time, a command must eventually be able to say **who or what issued
it**. Nothing needs to carry an author today, but no design should make adding
one a rewrite.

## Ownership and permission

A project has an **owner**: the person who created it, or the person ownership
was later transferred to. Ownership is about the project's governance — who may
invite, revoke, transfer and delete.

**Permission** is a different thing. It is scoped to a capability, it may be
one-time, session-based, dated or ongoing, and it is always revocable. When
someone needs to do something they are not yet permitted to do, they are
granted a permission — either for that one action or ongoing — and the owner
keeps their ownership.

> **Rule**
>
> Ownership ≠ Permission. Ownership is never transferred to satisfy an ordinary
> request for authority, and transfer is a deliberate workflow of its own.

Expiry looks forward. A permission that lapses blocks the next action; it never
undoes work already done.

## Guests and invitations

An owner invites one person at a time, by link for someone who has an account
and by a one-time code for someone who does not. The owner chooses what the
invitation grants and how long it lasts.

An invitation is a ticket, not a key: it is opaque, single-use by default,
expiring, revocable, and exchanged once for an identity that carries all later
access. Project content appears only after a successful claim.

Someone without an account may still take part, and still has a name. A guest
receives a project-scoped identity, so the history says *Guest "Maria" renamed
Entity "Student"* rather than *Unknown changed project*.

## What this requires of decisions taken now

- Do not describe ERDFlow as single-user, ownerless or unshared. It is those
  things in V1 only, and the plan should say so that way.
- Ownership, permissions, invitations and guests are specified in
  [ADR-019](adr/ADR-019-PRINCIPALS-OWNERSHIP-AND-PERMISSIONS.md) and
  [ADR-020](adr/ADR-020-INVITATIONS-AND-GUEST-ACCESS.md). Neither is built.
- Stable identity, atomic semantic commands and versioned project files stay
  the foundation, because merging concurrent work depends on all three.
- A start screen, a project list and a project file should each be able to
  gain an owner without their structure changing.
