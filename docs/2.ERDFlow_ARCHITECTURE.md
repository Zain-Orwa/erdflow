# ERDFlow Architecture

**Document:** `docs/ARCHITECTURE.md`  
**Status:** Architecture v0.1  
**Product:** ERDFlow  
**Scope:** Standalone cross-platform visual database designer  
**Primary desktop stack:** Qt 6 + C++20  
**Future core direction:** Rust behind a clean boundary

---

# 1. Purpose

This document defines how ERDFlow is structured internally.

`PRODUCT.md` defines **what ERDFlow does**.

`ARCHITECTURE.md` defines **how ERDFlow is organized so that the product can be built safely, tested independently, remain responsive, and evolve without coupling the core database logic to Qt, files, databases, AI, or future Exentury integration**.

The architecture must support the product principle:

> Draw once, progressively refine.

The same project may move through:

```text
Conceptual ERD
      ↓
Relational Schema
      ↓
Physical / Table Design
      ↓
SQL
      ↓
Data
```

These stages must remain connected without becoming one giant tightly coupled model.

---

# 2. Architecture Goals

ERDFlow architecture should:

1. Keep the database/domain logic independent of Qt.
2. Keep file formats independent of domain classes.
3. Support deterministic database transformations.
4. Preserve user edits when upstream models change.
5. Support controlled change propagation between compatible modeling levels.
6. Support undo/redo without coupling domain commands to Qt.
7. Allow the UI to remain responsive during heavy work.
8. Support versioned `.erdx` persistence and future migrations.
9. Support multiple import formats through adapters.
10. Support a Live Data Grid without assuming all data is always loaded into memory.
11. Make testing possible without launching the GUI.
12. Keep the C++ ↔ future Rust boundary clean.
13. Remain portable across macOS, Linux, and Windows.
14. Avoid designing cloud, AI, plugins, or ERP behavior into the core before they are needed.

---

# 4. Dependency Rule

Dependencies flow toward the core:

```text
Presentation
     ↓
Application
     ↓
Domain
```

Infrastructure depends on interfaces defined closer to the Application/Core side.

Forbidden dependencies include:

```text
Domain → Qt
Domain → QGraphicsItem
Domain → QFile
Domain → JSON serializer
Domain → SQL database driver
Domain → AI SDK
```

The Domain should remain usable in unit tests, command-line tools, future services, a future Rust core, and alternative frontends.

---

# 5. Presentation Layer

The Presentation layer is the Qt 6 desktop interface.

Responsibilities include:

- main window,
- menu/ribbon,
- explorer panel,
- properties panel,
- conceptual canvas,
- relational schema workspace,
- table design workspace,
- SQL workspace,
- Data Workspace,
- status bar,
- dialogs,
- progress UI,
- notifications,
- user confirmation prompts,
- keyboard and pointer interaction.

The Presentation layer does not own database meaning.

## 5.1 Critical Canvas Rule

A Qt graphics object is not a database object.

Wrong:

```text
QGraphicsRectItem = Entity
```

Correct:

```text
Domain Entity
     │
     ▼
Qt EntityGraphicsItem
```

The domain entity exists independently of how it is drawn.

## 5.2 UI Types Must Not Leak Downward

The Domain should prefer standard C++ types such as `std::string`, `std::vector`, `std::optional`, and `std::chrono`.

Qt-specific types such as `QString`, `QVector`, `QDateTime`, and `QGraphicsItem` belong in Presentation or adapter code unless a specific exception is explicitly documented.

---

# 6. Application Layer

The Application layer coordinates user intentions.

Responsibilities include:

- create/open/save project,
- create/rename/delete entities,
- add or edit attributes,
- create relationships,
- change cardinality and participation,
- convert Conceptual → Relational,
- review generated changes,
- accept/reject propagation,
- undo/redo coordination,
- import/export coordination,
- background task orchestration,
- Data Workspace operations.

The Application layer contains use-cases, not Qt rendering logic or low-level file-format logic.

---

# 7. Domain Layer

The Domain layer contains the core database-design meaning of ERDFlow and must remain independent of Qt.

Initial major domain areas:

```text
Project
├── ConceptualModel
├── RelationalSchema
├── PhysicalModel
├── DataWorkspaceMetadata
├── CrossLevelMappings
└── ProjectSettings
```

The exact C++ class layout is not locked yet; the responsibility boundaries are.

---

# 8. Stable Identity

Every meaningful semantic object must have a stable identity. Names are not identities.

Examples:

```text
EntityId
AttributeId
RelationshipId
SpecializationId
RelationId
SchemaAttributeId
TableId
ColumnId
ConstraintId
IndexId
PageId
```

Example:

```text
EntityId: E-104
Name: Student
```

If the user renames `Student` to `UniversityStudent`, ERDFlow should still know it is the same entity: `E-104`.

Stable identity is required for rename detection, undo/redo, conversion mappings, controlled propagation, diff/review, persistence, future collaboration, future AI review, and debugging.

## 8.1 ID Representation

The exact representation is deferred. Possible implementations include UUID, ULID, typed integer IDs, or another generated identifier.

---

# 9. Conceptual Model

The Conceptual Model represents database meaning using Chen-style concepts.

It should eventually contain entities, attributes, relationships, specialization/generalization, and pages.

Relationship notation includes:

```text
1:1
1:M
M:1
M:M
```

`M:M` is the standard ERDFlow notation for many-to-many relationships.

Pages are layout/presentation metadata associated with the project, not separate database models.

---

# 10. Relational Schema Model

The Relational Schema should eventually contain relations, schema attributes, primary keys, foreign keys, unique constraints, nullability, comments, and logical structural metadata.

Generated Schema remains editable.

Schema objects have their own stable IDs and are connected to conceptual objects through mapping/provenance metadata, not by name equality.

---

# 11. Physical Model

The Physical Model contains implementation-level structures such as tables, columns, physical data types, length/precision/scale, constraints, indexes, identity/auto-increment, dialect-specific options, and comments.

Physical-only decisions must not pollute Conceptual or Relational models.

---

# 12. Cross-Level Mapping and Provenance

ERDFlow must record how generated elements were derived.

Examples:

```text
Conceptual Entity E-104
        │
        │ generated
        ▼
Relation R-208
```

```text
Conceptual M:M Relationship REL-11
        │
        │ conversion rule
        ▼
Junction Relation R-310
```

Mappings/provenance should eventually record source element, target element, mapping kind, conversion rule, and generation baseline.

This metadata is foundational for explaining conversions, controlled propagation, safe regeneration, diff/review, preserving manual work, and debugging.

---

# 13. Deterministic Conversion Engine

Known database transformations use deterministic rules.

Examples:

```text
Strong Entity → Relation
1:M → Foreign key on the M side
M:M → Junction relation
Multivalued Attribute → Separate relation
Associative Entity → Relation
Weak Entity → Owner key combined with weak-entity identification
Generalization / Specialization → Selected relational mapping strategy
```

The conversion engine must not depend on the UI.

Conceptually:

```cpp
RelationalConversionResult convertToRelational(
    const ConceptualModel& conceptual,
    const ConversionOptions& options);
```

Later:

```cpp
PhysicalConversionResult convertToPhysical(
    const RelationalSchema& schema,
    Dialect dialect,
    const ConversionOptions& options);
```

```cpp
SqlGenerationResult generateSql(
    const PhysicalModel& physical,
    Dialect dialect);
```

Exact signatures are not locked.

Conversion should produce a candidate target model, mappings/provenance, applied rules, warnings, errors, and unresolved decisions. It should not silently mutate the source model.

---

# 14. Validation

Validation belongs to the Domain/Core.

Examples include missing identifiers, invalid cardinality, unresolved specialization strategy, missing logical type, invalid key structure, or inconsistent foreign-key mapping.

Validation should return structured facts. The UI decides how to present them.

Example:

```text
Errors: 1
Warnings: 2
Satisfied checks: 17
```

The UI may turn those facts into a readiness percentage.

---

# 15. Commands and Semantic Operations

Meaningful user edits should be represented as semantic operations.

Examples:

```text
CreateEntity
RenameEntity
DeleteEntity
AddAttribute
RenameAttribute
ChangeLogicalType
CreateRelationship
ChangeCardinality
ChangeParticipation
CreateRelation
RenameRelation
AddForeignKey
AddIndex
```

Prefer explicit semantic operations over repeatedly inferring intent by comparing giant object graphs.

---

# 16. Undo / Redo

Undo/redo is an Application concern.

Qt may use `QUndoStack`/`QUndoCommand`, but ERDFlow domain/application commands must not depend on Qt.

Conceptually:

```text
ERDFlow Application Command
       │
       ├── execute
       ├── inverse/reverse
       └── semantic metadata
               │
               ▼
Qt Undo Adapter
               │
               ▼
QUndoStack
```

---

# 17. Controlled Change Propagation

ERDFlow does not use an always-running two-way synchronization engine.

Normal direction:

```text
Conceptual
     │
     │ deterministic conversion
     ▼
Relational Schema
```

Schema edits stay in Schema by default.

When a Schema edit has a meaningful Conceptual equivalent, ERDFlow may offer to propagate it back.

Example:

```text
Schema:
Student.Name
→ Student.FullName
```

ERDFlow may ask:

```text
This modification can also be represented
in the Conceptual model.

Apply to Conceptual ERD too?

[ Yes ] [ No ]
```

Technical-only changes such as indexes, implementation-only surrogate keys, DB-specific constraints, physical data types, and technical helper columns do not move upstream automatically.

Propagation principle:

```text
Detect → Explain → Ask → Apply
```

Never silently propagate ambiguous or meaning-changing modifications.

---

# 18. Generation Baselines

Safe regeneration requires remembering what was generated previously.

Example:

```text
Conceptual v1
      ↓
Generated Schema Baseline v1
```

If the user edits the Schema and later Conceptual changes, ERDFlow should not blindly replace the current Schema.

The architecture should support:

```text
                Previous Generated Baseline
                        Schema v1
                       /         \
                      /           \
Current Schema                    New Candidate
(user edits)                      from Conceptual v2
                      \           /
                       \         /
                      Review / Merge
```

This allows ERDFlow to distinguish previous generated state, user manual modifications, and new upstream changes. The exact merge algorithm is deferred.

---

# 19. Diff and Review

ERDFlow will need structural and semantic diffing, but Architecture v0.1 does not define one giant generic diff engine.

Preferred foundation:

1. stable IDs,
2. semantic commands,
3. mappings/provenance,
4. generation baselines,
5. targeted diff logic.

A future diff may classify Added, Removed, Renamed, Modified, Technical-only, Semantic, or Ambiguous changes.

---

# 20. Persistence Boundary

The Domain must not serialize itself directly.

Avoid spreading methods such as `Entity::toJson()` throughout the domain.

Use:

```text
Domain Project
      ↓
Project Document Mapper
      ↓
Versioned ERDFlow Document
      ↓
Serializer
      ↓
.erdx
```

This separates database meaning, persistence representation, and storage format.

---

# 21. `.erdx` Project Format

`.erdx` is the working ERDFlow native project extension.

The format must be versioned from the beginning.

```json
{
  "format_version": 1,
  "project": {}
}
```

The exact internal storage encoding is not yet locked.

Future versions must support migration:

```text
.erdx v1
    ↓ migration
.erdx v2
```

---

# 22. Project Storage Interface

Application/Core should depend on a storage abstraction.

Conceptually:

```cpp
class ProjectStore
{
public:
    virtual Project load(/* source */) = 0;
    virtual void save(/* destination */, const Project&) = 0;
};
```

Exact signatures are deferred. Infrastructure provides implementations such as `ErdxProjectStore`.

---

# 23. Safe Saving

Project saving must protect against partially written project files.

Conceptually:

```text
Write temporary file
      ↓
Validate successful write
      ↓
Commit/replace destination
```

Qt's `QSaveFile` is a strong candidate for the desktop adapter.

---

# 24. Import Architecture

Import is a core product capability independent of AI.

```text
External File
      ↓
Format Detection
      ↓
Importer / Parser
      ↓
Structured Intermediate Representation
      ↓
Validation
      ↓
Preview
      ↓
Mapping / Options
      ↓
Application Command
      ↓
Project
```

Importers must not manipulate Qt canvas objects.

Conceptually:

```text
Importer
├── SqlImporter
├── CsvImporter
├── JsonImporter
├── FutureExcelImporter
├── FutureDatabaseMetadataImporter
└── FuturePluginImporter
```

---

# 25. Import Intermediate Representation

Imported content should not immediately become canvas widgets or final domain objects.

A structured intermediate representation should support parser-specific data, warnings, inferred types, candidate keys, candidate mappings, preview, and user correction.

The exact IR format requires a later ADR.

---

# 26. Data Workspace Architecture

The Data Workspace should not assume that all rows are permanently stored in one in-memory vector.

Use a Data Source abstraction:

```text
Data Workspace
      │
      ▼
Data Source
      │
      ├── ProjectLocalDataSource
      ├── ImportedDataSource
      └── FutureDatabaseDataSource
```

For small local/sample data, in-memory storage may be appropriate. For future large connected databases, data should be fetched in pages/chunks or queried directly.

---

# 27. Live Data Grid

The Qt Data Workspace may use:

```text
QTableView
     ↓
Sort / Filter Model
     ↓
Qt Table Model Adapter
     ↓
ERDFlow Data Source
```

Possible data sources:

```text
Local Project Data
Imported Data
Future Database Connection
```

Sorting changes the current view; it does not redefine permanent physical row order.

For local data, sorting may occur through a Qt proxy or local data view. For large remote data, sorting should eventually be pushed to the database using `ORDER BY` rather than loading all rows into memory.

Future remote editing must distinguish local/sample data, imported data, and live connected database data.

---

# 28. SQL Generation

SQL generation is a Core/Domain capability using the Physical Model plus a dialect abstraction.

```text
Physical Model
      │
      ▼
SQL Generator
      │
      ├── PostgreSQL Dialect
      ├── MySQL Dialect
      ├── SQLite Dialect
      ├── SQL Server Dialect
      └── Future Dialects
```

The UI displays generated SQL but does not implement SQL-generation rules.

---

# 29. Dialect Boundary

Database dialect differences must be isolated.

Examples include type mappings, identity syntax, quoting rules, constraints, index syntax, and engine-specific options.

Do not scatter database-specific `if` statements through unrelated code.

---

# 30. Concurrency and Background Work

The Qt UI thread must remain responsive.

Heavy work should be executable through background tasks.

```text
UI Thread
│
├── rendering
├── interaction
├── ribbon
├── canvas updates
└── dialogs

Background Task System
│
├── large imports
├── validation
├── conversions
├── auto-layout
├── large save/load
├── SQL generation for large projects
├── reverse engineering
└── future AI operations
```

Core operations must be callable independently of the UI thread.

Possible Qt mechanisms include `QtConcurrent`, `QThreadPool`, `QRunnable`, or dedicated worker objects. The exact choice is deferred.

---

# 31. Thread Safety

Preferred direction:

```text
UI reads view state / snapshots
Background task receives immutable input snapshot
Background task produces result
Application validates result
Application applies accepted result
UI updates
```

Do not allow arbitrary background threads to mutate the live Qt UI or project model directly.

---

# 32. Project Mutation Control

Meaningful Project mutations should flow through controlled Application commands.

Avoid:

```text
random widget → directly edits domain structure
```

Prefer:

```text
widget event
    ↓
Application Command
    ↓
Domain mutation
    ↓
Result/event
    ↓
UI refresh
```

---

# 33. Layout State vs Semantic State

ERDFlow contains two kinds of information.

Semantic examples:

- Entity Student
- Attribute StudentID
- Relationship Enrolled
- cardinality M:M
- logical type Integer

Visual/layout examples:

- x/y position
- connector bend points
- zoom
- page
- collapsed panel state
- selection

They must not be treated as the same thing.

---

# 34. View Models / Presentation Models

The Presentation layer may use Qt-oriented models such as `ConceptualCanvasViewModel`, `ExplorerViewModel`, `PropertiesViewModel`, `SchemaTableModel`, and `DataGridTableModel`.

These may expose Qt-friendly data but must not replace the Domain model.

---

# 35. Future Rust Core Boundary

Rust is a future implementation direction for reusable core logic. It is not required for the first desktop milestone.

Potential Rust responsibilities later include project model, validation, conversion, mappings/provenance, import parsers, diff, SQL generation, and project-format logic.

```text
Qt / C++ Presentation
        │
        │ clean structured boundary
        ▼
Reusable Core
        │
        └── may gradually become Rust
```

---

# 36. Rust Interop Rule

Do not design current core interfaces around Qt objects.

Bad:

```cpp
processEntity(QGraphicsItem*);
```

Good conceptual boundary:

```text
Structured Domain Input
        ↓
Core Operation
        ↓
Structured Result
```

Possible future FFI approaches include C ABI, CXX bridge, or another safe interoperability layer. No FFI mechanism is locked in Architecture v0.1.

---

# 37. Testing Architecture

ERDFlow must be testable without launching the GUI.

Domain tests include conversion rules, validation, mappings/provenance, and change classification.

Application tests include commands, undo/redo semantics, conversion orchestration, propagation decisions, and import workflow.

Infrastructure tests include `.erdx` save/load, migrations, parsing, and safe file saving.

UI tests include canvas creation, selection, move, properties editing, and Data Grid interaction.

Domain tests should be the fastest and most numerous.

---

# 38. Cross-Platform Rules

ERDFlow targets macOS, Linux, and Windows.

Rules:

1. Avoid unnecessary OS-specific code.
2. Wrap unavoidable platform-specific behavior behind adapters.
3. Use portable project paths inside `.erdx`.
4. Avoid machine-specific absolute paths unless explicitly required.
5. Keep core logic independent of OS APIs.
6. Test project portability between supported systems.

---

# 39. Error Handling

Domain and Application layers should return structured errors rather than display UI dialogs directly.

Examples:

```text
ConversionError
ValidationIssue
ImportError
PersistenceError
```

Presentation decides whether these become a dialog, status message, warning panel, or readiness indicator.

---

# 40. Logging and Diagnostics

ERDFlow should eventually support structured diagnostics for project, conversion, import, persistence, performance, database, UI, and future AI areas.

Logging must not expose sensitive imported or connected database data by default.

---

# 41. Security Boundaries

Imported files are untrusted input.

Importers must validate input, handle malformed data, avoid arbitrary code execution, enforce reasonable resource limits, and report errors safely.

Imported SQL is parsed as text/model input and must not be executed automatically.

---

# 42. Architecture for Future AI

AI remains outside the Domain core.

```text
AI Provider
      ↓
AI Adapter
      ↓
Structured Proposal
      ↓
Core Validation
      ↓
Application Review
      ↓
User Accept / Modify / Reject
```

AI never gets direct authority to mutate the project.

---

# 43. Architecture for Future Plugins

Plugins are deferred. Potential future plugin areas include importers, exporters, SQL dialects, database connectors, validation rules, and AI providers.

Plugin APIs are not part of V1.

---

# 44. Architecture for Future Exentury Integration

ERDFlow remains standalone.

ERDFlow domain code must not depend on ERP concepts such as HR, finance, CRM, payroll, or operations.

Future integration should occur through clean service/API boundaries.

---

# 45. First Implementation Architecture

The first milestone is the Conceptual Chen ERD Editor.

Only the minimum architecture needed for that milestone should be implemented.

```text
Qt Application Shell
        ↓
Conceptual Canvas
        ↓
Application Commands
        ↓
Minimal Conceptual Domain Model
```

The first milestone needs Entity, Attribute, Relationship, Connector, 1/M labels, selection, move, edit, delete, zoom/pan, and a properties panel.

Do not implement SQL generation, the full Data Grid, AI, cloud, plugins, Exentury integration, or Rust FFI yet.

# 47. Architecture Decisions Locked in v0.1

1. Qt 6 + C++20 for the desktop application.
2. Presentation, Application, Domain, and Infrastructure boundaries.
3. Domain must not depend on Qt.
4. Qt graphics objects are views, not database/domain objects.
5. Stable IDs are required for semantic objects.
6. Names are not object identities.
7. Cross-level mappings/provenance are required.
8. Deterministic database transformations belong in the core.
9. `M:M` is the ERDFlow many-to-many notation.
10. Schema edits do not automatically update Conceptual.
11. Eligible Schema changes may be propagated to Conceptual only after user confirmation.
12. Technical/physical-only changes remain downstream.
13. Controlled propagation follows `Detect → Explain → Ask → Apply`.
14. Safe regeneration requires generated baselines.
15. Semantic commands are preferred over relying only on structural diffing.
16. Domain/application commands must not depend on Qt undo classes.
17. `.erdx` persistence is separated from Domain models.
18. `.erdx` is versioned from the beginning.
19. Importers do not manipulate UI widgets directly.
20. Data Workspace uses a Data Source abstraction.
21. Sorting/filtering are view/query operations, not permanent row ordering.
22. Heavy work must be executable outside the UI thread.
23. Future Rust must sit behind structured interfaces.
24. Rust FFI technology is not selected yet.
25. AI and plugins remain optional adapters, not Domain dependencies.

# 49. Architecture Invariants

1. The Qt UI is not the database model.
2. The Domain does not know about Qt.
3. File-format details do not pollute Domain entities.
4. Generated outputs are reviewable and editable.
5. Manual downstream work is not destroyed silently.
6. Schema → Conceptual propagation is explicit and user-approved.
7. Technical implementation details do not automatically move upstream.
8. Semantic objects have stable identities.
9. Conversions preserve provenance/mapping information.
10. Long-running operations do not block the UI thread.
11. Import does not directly manipulate UI widgets.
12. The Data Grid does not require all future database rows to live permanently in memory.
13. AI never silently mutates the project.
14. ERDFlow remains useful as a standalone desktop product.

# 50. Architecture Summary

ERDFlow is built around a reusable database-design core surrounded by adapters.

```text
                     USER
                      │
                      ▼
             Qt 6 Presentation
                      │
                      ▼
                Application
          Commands / Use Cases
         Review / Undo / Tasks
                      │
                      ▼
                  Domain
        ┌─────────────┼─────────────┐
        │             │             │
  Conceptual     Relational      Physical
        │             │             │
        └────── Mapping / Provenance
                      │
              Validation / Conversion
                      │
                      ▼
            Structured Core Results

Infrastructure adapters connect the core to:

.erdx
SQL
CSV
JSON
Exports
Future databases
Future AI
Future plugins
```

The guiding architecture principle is:

> Keep database meaning in the core, keep interaction in the UI, and keep external systems behind adapters.
