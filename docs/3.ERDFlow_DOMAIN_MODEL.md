# ERDFlow Domain Model

**Document:** `docs/DOMAIN_MODEL.md`  
**Status:** Domain Model v0.1  
**Product:** ERDFlow

---

# 1. Purpose

This document defines the core semantic model of ERDFlow.

It answers questions such as:

- What is a Project?
- What is an Entity?
- What is an Attribute?
- What is a Relationship?
- How are Conceptual, Relational, Physical, SQL, and Data stages connected?
- What objects require stable IDs?
- What information is semantic and what information is only visual/layout state?
- What information is allowed to propagate between stages?

This document does not define Qt widgets or file serialization details.

The Domain Model must remain independent of Qt.

---

# 2. Core Principle

ERDFlow follows:

> Draw once, progressively refine.

A single ERDFlow project may contain several representations of the same database design:

```text
Project
│
├── Conceptual Model
├── Relational Schema
├── Physical Model
├── SQL Output
└── Data Workspace
```

These are connected, but they are not the same model.

Each level has its own responsibility.

---

# 3. Project

`Project` is the top-level semantic container.

Conceptually:

```text
Project
├── ProjectId
├── Metadata
├── ConceptualModel
├── RelationalSchema
├── PhysicalModel
├── CrossLevelMappings
├── GenerationBaselines
├── ProjectSettings
└── DataWorkspaceMetadata
```

Possible metadata includes:

- project name,
- description,
- created time,
- modified time,
- project format version,
- optional author information,
- optional comments.

The exact C++ representation is not locked yet.

# 4. Stable IDs

Every meaningful semantic object must have a stable identity.

Names are not identities.

Example:

```text
EntityId: E-104
Name: Student
```

If `Student` is renamed to `UniversityStudent`, the identity remains:

```text
EntityId: E-104
```

ERDFlow should eventually define typed identifiers such as:

```text
ProjectId
EntityId
AttributeId
RelationshipId
SpecializationId
PageId

RelationId
SchemaAttributeId
PrimaryKeyId
ForeignKeyId

TableId
ColumnId
ConstraintId
IndexId

MappingId
BaselineId
```

The exact encoding is deferred.

The Conceptual Model represents business/domain meaning using Chen-style modeling.

Conceptually:

```text
ConceptualModel

├── Attributes
├── Relationships
├── Specializations
├── Pages

```

# 6. Entity

An `Entity` represents a meaningful thing or concept in the modeled domain.

Examples:

- Student
- Course
- Employee
- Customer
- Product

Possible properties:

```text
Entity
├── EntityId
├── Name
├── Description
├── Comment
├── Kind
├── Attributes
├── PageMembership
└── Metadata
```

Entity kinds initially include:

```text
Strong
Weak
```

A weak entity may also reference:

```text
OwnerEntityId
IdentifyingRelationshipId
```

where applicable.

---

# 7. Attribute

An `Attribute` represents a property of an Entity or, where valid, a Relationship.

Examples:

```text
StudentID
Name
BirthDate
Email
Grade
RegistrationDate
```

Possible properties:

```text
Attribute
├── AttributeId
├── Name
├── Kind
├── LogicalType
├── IdentifierFlag
├── RequiredFlag
├── UniqueFlag
├── Description
├── Comment
├── ParentAttributeId?
└── DerivedFrom?
```

Attribute kinds:

```text
Normal
Key
Composite
Multivalued
Derived
PartialKey
```

---

# 8. Composite Attribute

A Composite Attribute contains other attributes.

Example:

```text
Name
├── FirstName
├── MiddleName
└── LastName
```

The parent and child relationship should be represented semantically, not inferred from canvas position.

Conceptually:

```text
Attribute Name
ID: A-10

Children:
A-11 FirstName
A-12 MiddleName
A-13 LastName
```

---

# 9. Multivalued Attribute

A Multivalued Attribute can contain more than one value for the same entity instance.

Example:

```text
Student
   |
PhoneNumber
```

A later deterministic conversion may map a multivalued attribute to a separate relation.

---

# 10. Derived Attribute

A Derived Attribute is computed or inferred from other information.

Example:

```text
BirthDate
   ↓
Age
```

A derived attribute should be marked semantically.

It must not be identified only because the UI draws it differently.

---

# 11. Partial Key

A Partial Key is used with a Weak Entity.

Example:

```text
Employee
    |
Dependent
    |
DependentName
```

`DependentName` may be a partial key when combined with the owner key.

The exact conversion rules will be defined in the transformation design.

---

# 12. Logical Type

Convertible Conceptual Mode may assign database-independent logical types.

Initial logical types:

```text
Text
Integer
Decimal
Boolean
Date
DateTime
Binary
UUID
```

Possible future additions are allowed.

Logical types belong to conceptual/logical meaning.

DBMS-specific types such as:

```text
VARCHAR(100)
NVARCHAR(100)
BIGINT
SERIAL
```

belong primarily to the Physical Model.

---

# 13. Relationship

A `Relationship` connects entities semantically.

Example:

```text
Student --- Enrolled --- Course
```

Possible properties:

```text
Relationship
├── RelationshipId
├── Name
├── Participants
├── Attributes
├── IdentifyingFlag
├── AssociativeFlag
├── Description
├── Comment
└── Metadata
```

A relationship should not store meaning only through visual line objects.

---

# 14. Relationship Participant

A relationship may involve two or more entity participants.

Each participant should carry its own relationship-side information.

Conceptually:

```text
RelationshipParticipant
├── EntityId
├── Cardinality
├── Participation
└── RoleName?
```

This is important because cardinality and participation belong to the entity side of the relationship.

---

# 15. Cardinality

ERDFlow standard notation:

```text
1:1
1:M
M:1
M:M
```

For a specific participant side, the internal representation should preserve that side's maximum cardinality.

Conceptually:

```text
One
Many
```

The UI may render the pair as:

```text
1:M
```

or:

```text
M:M
```

The exact internal enum is deferred.

---

# 16. Ordinality / Minimum Participation Count

More detailed minimum/maximum rules may include:

```text
0..1
1..1
0..M
1..M
```

This means a participant may need:

```text
minimum
maximum
```

rather than only a single display string.

Example conceptually:

```text
min = 0
max = Many
```

This gives ERDFlow enough information for later conversion and validation.

---

# 17. Participation

Participation types:

```text
Total
Partial
```

Participation is stored per relationship participant.

Example:

```text
Relationship: Enrolled

Student:
    Cardinality = Many
    Participation = Total

Course:
    Cardinality = Many
    Participation = Partial
```

This may display as an `M:M` relationship while preserving each side's participation independently.

---

# 18. Relationship Attributes

Relationships may contain attributes.

Example:

```text
Student --- Enrolled --- Course

Enrolled:
- RegistrationDate
- Grade
- Attempt
```

These attributes belong semantically to the relationship.

They should not be forced into either entity.

---

# 19. Associative Entity

A relationship may later become an Associative Entity when it requires its own identity, attributes, or further relationships.

Example:

```text
Student --- Enrolled --- Course
```

may evolve into:

```text
Student --- Enrollment --- Course
```

with:

```text
Enrollment
├── RegistrationDate
├── Grade
└── Attempt
```

ERDFlow should preserve provenance when this transformation occurs.

The exact representation may use either:

- a dedicated associative-entity type,
- or an entity carrying associative-origin metadata.

This decision is still open.

---

# 20. Weak Entity

A Weak Entity depends on an owner/strong entity.

Possible semantic information:

```text
WeakEntity
├── EntityId
├── OwnerEntityId
├── IdentifyingRelationshipId
└── PartialKeyAttributeIds
```

Weakness must be semantic information.

It must not be inferred only from a double rectangle in the UI.

---

# 21. Generalization / Specialization

ERDFlow supports ISA structures.

Example:

```text
        Person
           |
          ISA
         /   \
        /     \
   Student   Employee
```

Possible model:

```text
Specialization
├── SpecializationId
├── SupertypeEntityId
├── SubtypeEntityIds
├── Constraint
└── Completeness
```

Constraint:

```text
Disjoint
Overlapping
```

Completeness:

```text
Total
Partial
```

# 22. Conceptual Modes

ERDFlow has one underlying Conceptual Model with two working modes:

```text
Basic / Learning
Convertible / Engineering
```

These modes do not create separate domain models.

Instead, Convertible Mode exposes or requires richer metadata.

Examples:

```text
LogicalType
IdentifierFlag
RequiredFlag
UniqueFlag
Description
Conversion readiness metadata
```

Basic Mode may hide that information from the user.

---

# 23. Conceptual Pages

Large conceptual diagrams may use multiple pages.

Pages organize presentation.

Conceptually:

```text
ConceptualPage
├── PageId
├── Name
└── LayoutReferences
```

An Entity remains the same semantic Entity even if its visual representation is moved to another page.

Page membership is not database meaning.

---

# 24. Semantic State vs Layout State

ERDFlow must distinguish semantic state from visual state.

## Semantic State

Examples:

```text
Student exists
StudentID is an identifier
Enrolled connects Student and Course
Enrolled is M:M
Student participation is Total
```

## Layout State

Examples:

```text
Student rectangle x/y
Attribute oval x/y
connector bend points
zoom level
selected item
page position
```

Moving an Entity on the canvas must not alter database meaning.

# 27. Relation

A `Relation` represents a logical relation.

Example:

```text
Student(
    StudentID,
    Name,
    Email
)
```

Possible properties:

```text
Relation
├── RelationId
├── Name
├── Attributes
├── PrimaryKey
├── ForeignKeys
├── UniqueConstraints
├── Comment
└── Metadata
```

A generated relation remains editable.

---

# 28. Schema Attribute

A relational attribute belongs to a Relation.

Possible properties:

```text
SchemaAttribute
├── SchemaAttributeId
├── Name
├── LogicalType
├── Nullable
├── Unique
├── Comment
└── Metadata
```

A Schema Attribute is not automatically identical to a Conceptual Attribute.

If it was generated from one, the connection is represented by mapping/provenance.

---

# 29. Primary Key

A Primary Key identifies rows in a Relation.

Conceptually:

```text
PrimaryKey
├── PrimaryKeyId
└── AttributeIds
```

Composite primary keys are supported naturally because the key contains multiple attribute IDs.

---

# 30. Foreign Key

A Foreign Key connects one Relation to another.

Conceptually:

```text
ForeignKey
├── ForeignKeyId
├── SourceRelationId
├── SourceAttributeIds
├── TargetRelationId
├── TargetAttributeIds
└── Metadata
```

A Foreign Key may be generated deterministically from a Conceptual relationship.

---

# 31. M:M Conversion

ERDFlow uses `M:M` for many-to-many relationships.

Example:

```text
Student M:M Course
```

Deterministic conversion:

```text
Student
Course
Enrolled
```

where `Enrolled` becomes a junction relation.

Conceptually:

```text
Enrollment
├── StudentID FK
├── CourseID FK
└── relationship attributes...
```

The conversion engine must store mappings between the original Conceptual relationship and the generated Relation.

# 41. Row

A Row is a set of values corresponding to a table/relation structure.

Conceptually:

```text
Row
├── RowIdentity?
└── Values
```

The exact representation depends on the Data Source.

For local/sample data, rows may live in memory.

For remote database data, rows may be streamed or paged.

ERDFlow must not assume the whole database table is always loaded into memory.

---

# 42. Row Ordering

A relational table has no guaranteed permanent row order unless a query explicitly requests ordering.

Therefore:

```text
Sort CreatedAt ↓
```

changes the displayed/query order.

It does not redefine a permanent physical order of rows.

A `CreatedAt` sort is possible only if such a column exists.

Changes may be classified as:


# 50. Controlled Schema → Conceptual Propagation

Schema changes remain in Schema by default.

When a change has a meaningful conceptual equivalent:

```text
Schema Change
      ↓
Eligibility Check
      ↓
Explain
      ↓
Ask User
      ↓
Yes / No
```

If Yes:

```text
apply conceptual equivalent
```

If No:

```text
keep schema-only change
```

This is controlled propagation.

It is not continuous two-way synchronization.

---

# 51. Conceptual → Schema Regeneration

Conceptual → Schema is the normal forward generation direction.

When Conceptual changes after Schema exists:

```text
Current Conceptual
      ↓
Generate Candidate Schema
```

ERDFlow should compare that candidate against:

```text
Previous Generated Baseline
Current User-Edited Schema
```

before replacing anything.

The result is a reviewable set of changes.

# 56. Domain Invariants

The following rules must always remain true.

## Invariant 1

Semantic objects have stable identities.

## Invariant 2

Names are editable labels, not identities.

## Invariant 3

Qt objects are never the authoritative semantic model.

## Invariant 4

Visual position does not define semantic meaning.

## Invariant 5

Relationship cardinality/participation is attached to relationship participants, not floating UI text.

## Invariant 6

ERDFlow uses `M:M` for many-to-many notation.

## Invariant 7

Logical types remain separate from DBMS-specific physical types.

## Invariant 8

Generated downstream objects retain provenance.

## Invariant 9

Schema edits do not silently modify Conceptual.

## Invariant 10

Technical/physical-only changes do not automatically propagate upstream.

## Invariant 11

Conceptual → Schema regeneration must protect manual Schema work.

## Invariant 12

The Data Workspace does not assume all future rows fit in memory.

## Invariant 13

Sorting rows changes a view/query order, not permanent relational row order.

# 58. Forward Lineage Example

Example project:

```text
Conceptual
----------

Student
Course

Student M:M Course
Relationship: Enrolled
Attribute: Grade
```

Conversion:

```text
Relational
----------

Student(...)
Course(...)
Enrollment(
    StudentID,
    CourseID,
    Grade
)
```

Lineage:

```text
Entity Student
    ↓
Relation Student

Entity Course
    ↓
Relation Course

Relationship Enrolled
    ↓
Relation Enrollment

Relationship Attribute Grade
    ↓
Schema Attribute Enrollment.Grade
```

Later:

```text
Relation Enrollment
    ↓
Physical Table Enrollment
    ↓
SQL CREATE TABLE Enrollment ...
```

This lineage should be recorded through mappings/provenance.

---

# 59. Back-Propagation Example

Suppose:

```text
Conceptual Attribute:
Student.Name

Generated Schema Attribute:
Student.Name
```

The user changes Schema:

```text
Student.Name
→ Student.FullName
```

Because provenance links the schema attribute to the conceptual attribute, ERDFlow can determine that a possible semantic equivalent exists.

Then:

```text
Schema change
      ↓
Mapping lookup
      ↓
Conceptual equivalent exists
      ↓
Ask user
```

If accepted:

```text
Conceptual Student.Name
→ Student.FullName
```

If declined:

```text
Conceptual remains unchanged
Schema keeps FullName
```

---

# 60. Technical-Only Change Example

Suppose the user adds:

```text
INDEX idx_student_email
```

to the Physical Model.

Classification:

```text
Technical / PhysicalOnly
```

Result:

```text
No Conceptual propagation offered
```

This preserves separation of abstraction levels.

# 61. Domain Model v0.1 Locked Decisions

The following are accepted:

1. `Project` is the top-level semantic container.

2. Conceptual, Relational, Physical, SQL, and Data are connected but distinct concerns.

3. Stable semantic IDs are required.

4. Names are not identities.

5. Conceptual entities, attributes, relationships, and specializations are pure domain concepts.

6. Relationship-side metadata is modeled per participant.

7. `M:M` is the many-to-many notation.

8. Participation is stored per relationship participant.

9. Semantic state and layout state are separate.

10. Conceptual and Convertible modes use the same underlying model.

11. Relational objects have their own IDs.

12. Physical objects have their own IDs.

13. Logical and physical data types remain separate.

14. Cross-level mappings/provenance are required.

15. Generation baselines are required conceptually.

16. Schema → Conceptual changes use controlled, user-approved propagation.

17. Conceptual → Schema is the primary deterministic generation direction.

18. Technical/physical-only changes remain downstream.

19. Data Workspace uses a Data Source abstraction.

20. Sorting changes view/query order, not physical row order.

21. Conversion results are structured and reviewable.

22. Validation returns structured issues.

# 63. First Domain Implementation Scope

The first implementation milestone does not require the full domain model.

For the Conceptual Chen ERD Editor, start with only:

```text
Project
└── ConceptualModel
    ├── Entity
    ├── Attribute
    ├── Relationship
    └── RelationshipParticipant
```

Plus minimal:

```text
Stable IDs
Names
Basic comments
Cardinality
Participation
Layout references
```

Do not implement the entire Relational, Physical, SQL, Data, mapping, and baseline systems before they are needed.

The architecture defines them now.

Implementation introduces them gradually.

# 64. Summary

ERDFlow's domain is built around one project with multiple connected representations.

The domain should express database meaning independently of:

- Qt,
- canvas widgets,
- files,
- SQL drivers,
- AI,
- future Exentury integration.

The key model flow is:

```text
Conceptual Model
      │
      │ deterministic conversion
      ▼
Relational Schema
      │
      ▼
Physical Model
      │
      ▼
SQL
      │
      ▼
Data Workspace
```

Mappings and provenance preserve lineage.

Stable IDs preserve identity.

Generation baselines protect manual work.

Controlled propagation allows selected meaningful Schema changes to be offered back to the Conceptual model without creating a continuously synchronized two-way system.

The guiding rule is:
