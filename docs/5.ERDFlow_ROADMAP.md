**Document:** `docs/ROADMAP.md`  
**Status:** Roadmap v0.2  
**Product:** ERDFlow  
**Current Stage:** Conceptual editor foundation — Phases 1–8 implemented locally; Phase 9 partial

**Phase 0 completed:** 2026-09-14; see [review evidence](PHASE_0_REVIEW.md).

---

# 1. Purpose

This document defines the order in which ERDFlow should be designed,
implemented, tested, measured, documented, and released.

It exists to prevent two major failures:

1. trying to build the whole product at once,
2. implementing later-stage systems before the foundations they depend on
   are proven.

ERDFlow will be built incrementally.

The development rule is:

> Understand → Design → Implement → Test → Measure → Document → Commit

Each phase should produce something testable and reviewable before the
next dependent phase begins.

---

# 2. Product Direction

ERDFlow is a desktop-first visual database design environment.

The product flow is:

```text
Conceptual ERD
      ↓
Relational Schema
      ↓
Physical / Table Design
      ↓
SQL
      ↓
Data
```

The central product principle is:

> Draw once, progressively refine.

The user should not repeatedly redraw the same database at every stage.

The stages are connected representations of the same ERDFlow project.

# 3. Roadmap v0.2 Corrections

This roadmap revision incorporates the architecture and scale review.

The most important corrections are:

1. **Stable Identity is now the first architectural decision to record.**

   Stable IDs are required before meaningful Domain implementation because
   mappings, provenance, undo/redo, regeneration, rename detection, and
   controlled propagation all depend on identity that survives renaming.

2. **Validation and conversion policy now has a dedicated ADR.**

   ERDFlow must explicitly distinguish:

   ```text
   domain invariant violations
   blocking conversion errors
   non-blocking warnings
   advisory information
   unresolved conversion decisions
   ```

3. **Native `.erdx` persistence is moved before the Conceptual Editor
   milestone.**

   The Conceptual Editor milestone requires save/load, so persistence must
   exist before that milestone can truthfully be called complete.

4. **Generation Baseline and Three-Way Regeneration Review are separated.**

   Capturing a baseline is not the same as safely reconciling:

   ```text
   previous baseline
   +
   current user-edited model
   +
   new generated candidate
   ```

5. **Safe Change Management is split into explicit sub-milestones.**

   Baseline/review and Schema → Conceptual back-propagation are both
   high-complexity systems and should not be hidden behind one vague
   progress label.

6. **The Live Data Grid remains intentionally late.**

   This is deliberate, not forgotten. ERDFlow first establishes the
   structural database flow and Data Source boundary. A visual mock may be
   explored earlier, but production Data Workspace behavior is not pulled
   forward just because it is demo-friendly.

# 4. Development Philosophy

## Rule 1 — One Phase at a Time

Do not implement future phases early merely because their architecture is
already documented.

## Rule 2 — Build the Smallest Useful Slice

Each phase should end with something that works.

## Rule 3 — Domain Before Convenience

Do not hide unclear database/domain decisions behind UI code.

## Rule 4 — Deterministic First

Known database rules use deterministic code.

AI comes later.

## Rule 5 — Protect Manual Work

Generated downstream models must not silently destroy user modifications.

## Rule 6 — UI Is Not the Domain

Qt widgets and graphics items represent domain objects.

They are not the authoritative database model.

## Rule 7 — Validate Before Transforming

Every deterministic transformation must operate under an explicit
validation policy.

## Rule 8 — Measure Performance

Do not optimize based only on assumptions.

## Rule 9 — Keep Future Boundaries Clean

Future Rust, AI, cloud, plugins, and Exentury integration must remain
possible without being implemented now.

# 16. ADR-009 — Validation Gates and Conversion Policy

This ADR is mandatory before the full conversion engine.

ERDFlow must distinguish at least:

```text
Domain Invariant Violation
Blocking Conversion Error
Non-Blocking Warning
Advisory / Information
Unresolved Conversion Decision
```

## Intended Direction

Validation runs before deterministic conversion.

A conversion must not proceed through a condition that makes a valid,
deterministic result impossible.

Non-blocking warnings may allow conversion after review.

The UI's `Convert Anyway` behavior must never mean:

> Ignore hard structural invalidity and produce arbitrary output.

Instead it means something closer to:

> Continue despite non-blocking warnings or explicitly accepted
> unresolved issues where the conversion policy allows it.

The exact rules are locked in ADR-009.

# 43. Phase 22 — Conversion Engine: Conceptual → Relational

## Goal

Implement deterministic Conceptual → Relational rules.

## Precondition

Conversion always invokes the validation/readiness policy defined by:

```text

```

## Intended Policy

```text
Blocking issue
→ conversion does not proceed

Non-blocking warning
→ conversion may continue after review/policy

Unresolved decision
→ request required decision or return an explicitly unresolved proposal,
   according to ADR-009
```

`Convert Anyway` must not bypass conditions that make deterministic output
invalid.

## Initial Rules

```text

→ Relation

1:M
→ FK on M side

M:M
→ Junction Relation

Multivalued Attribute
→ Separate Relation

Associative Entity
→ Relation

Weak Entity
→ Owner key + partial identification

Specialization
→ Selected mapping strategy
```

## Result

```text
RelationalConversionResult
├── CandidateSchema
├── AppliedRules
├── ValidationIssues
└── UnresolvedDecisions
```

Mappings/provenance become first-class in the next phase.

## Exit Criteria

Representative valid Conceptual models convert deterministically under
automated tests, and blocking invalid models are rejected according to
ADR-009.

Connect supported Schema import candidates from Phases 18–21 and verify
preview, review, apply, undo/redo, and save/load through the production
destination. Capture the initial generated reference before manual editing
so Phase 25 can preserve its distinction from the current Schema.

# 46. Phase 25 — Generation Baseline Foundation

## Goal

Capture the last accepted/generated downstream state required for future
safe regeneration.

This phase does **not** claim to solve three-way reconciliation yet.

## Baseline Concept

```text
Conceptual v1
     ↓ generation
Generated Schema Baseline v1
```

Then:

```text
User edits current Schema
```

ERDFlow must retain enough baseline information to know what was
originally generated.

## Requirements

A baseline should preserve the information required by the regeneration
design, including appropriate:

- target model state/snapshot or equivalent representation,
- source revision/reference,
- mapping/provenance state,
- baseline identity/version metadata.

Exact storage strategy follows architecture/scale decisions.

## Exit Criteria

ERDFlow can:

1. create a generation baseline,
2. persist/reload the baseline where required,
3. distinguish a user-edited current Schema from its last generated
   baseline,
4. preserve the mappings needed for the next phase.

This phase does not yet apply a new upstream candidate.

# 47. Phase 26 — Three-Way Regeneration Review

## Complexity

**High-complexity subsystem.**

Treat this phase as a major engineering effort, not a small utility.

## Goal

Safely review new Conceptual changes against existing user-edited Schema.

Inputs:

```text
Previous Generated Baseline
Current User-Edited Schema
New Candidate Schema
```

Output:

```text
Reviewable Change Proposal
```

## Example

```text
Baseline:
Student(Name)

Current Schema:
Student(FullName)
+ TechnicalCode

New Candidate from Conceptual:
Student(Name, DateOfBirth)
```

ERDFlow should be capable of distinguishing:

```text
manual rename/customization
new upstream addition
technical-only downstream addition
```

rather than replacing the current Schema.

## Diff Inputs

Use:

- stable IDs,
- mappings/provenance,
- baseline,
- semantic change information,
- structural comparison only where needed.

Do not infer identity only from names.

## Possible Change Classes

```text
Added
Removed
Renamed
Modified
Semantic
Technical
Ambiguous
Conflict
```

## Exit Criteria

A tested scenario containing:

```text
existing generated Schema
+
manual Schema edit
+
new Conceptual change
```

produces a reviewable proposal without destroying the manual edit.

No destructive automatic application is required to satisfy the phase.

# 48. Phase 27 — Controlled Schema → Conceptual Propagation

## Complexity

**High-complexity subsystem.**

This is not continuous synchronization.

## Goal

Implement:

```text
Detect → Explain → Ask → Apply
```

Schema edits remain Schema-only by default.

## Potentially Eligible Changes

Examples may include:

```text
rename mapped schema attribute
rename mapped relation/entity equivalent
meaningful logical metadata change
```

Eligibility must be semantic and mapping-aware.

## Not Automatically Eligible

Examples:

```text
Index
Physical data type
DB-specific constraint
Implementation-only helper column
Technical surrogate key
```

## Exit Criteria

At least one meaningful mapped Schema change can:

1. be recognized as eligible,
2. explain the Conceptual effect,
3. ask the user,
4. propagate only after `Yes`,
5. remain Schema-only after `No`.

# 90. Roadmap v0.2 Locked Decisions

1. Phase 0 closes before major implementation.

2. Stable identity is the first ADR and must exist before the Minimal
   Conceptual Domain.

3. Qt 6 + C++20 remain the current desktop direction.

4. Minimal Domain and Application-command foundations precede advanced
   modeling UI.

5. Generic canvas behavior precedes full Chen semantics.

6. Conceptual ERD is the first major product capability.

7. `M:M` is ERDFlow's many-to-many notation.

8. Basic and Convertible Conceptual modes share one underlying model.

9. Validation/readiness exists before the deterministic Schema conversion
   engine.

10. Validation/conversion policy has a dedicated ADR.

11. Blocking invalidity cannot be bypassed by a generic `Convert Anyway`
    action.

12. Versioned `.erdx` persistence exists before the Conceptual Editor
    milestone is declared complete.

13. Import is deterministic and independent of AI.

14. Initial deterministic import formats are SQL, CSV, and JSON.

15. Conceptual → Relational conversion is deterministic and
    validation-gated.

16. Mapping/provenance follows the initial conversion engine and uses
    stable identity.

17. Relational Schema remains editable.

18. Generation Baseline is a dedicated foundation phase.

19. Safe regeneration uses baseline + current + candidate review.

20. Three-way regeneration review is treated as a high-complexity
    subsystem.

21. Schema → Conceptual propagation is separate, optional, eligible, and
    user-approved.

22. Physical Model follows Relational Schema.

23. Relational → Physical transformation follows the same general
    validation-gate principle.

24. SQL generation follows Physical Design.

25. Production Data Workspace remains intentionally later in the roadmap.

26. Data Workspace uses a Data Source abstraction.

27. Live Data Grid sorting changes view/query order, not permanent row
    order.

28. Performance optimization is measurement-driven.

29. Background work is formalized before heavy workflows become
    production-critical.

30. Rust is evaluated later rather than introduced on schedule.

31. AI, cloud, plugins, and Exentury remain future phases.

32. ERDFlow must be a strong standalone desktop product before ecosystem
    expansion.
